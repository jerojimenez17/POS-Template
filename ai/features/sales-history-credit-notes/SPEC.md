# Sales history and credit-note safety — Technical Specification

## Status and scope

- **Stage:** G1 architecture/specification for the approved TDD work.
- **Implementation boundary:** this change covers `searchBill` paid-sale discovery/classification, the full-sale credit-note workflow and permission gate, the related public ARCA billing-action trust boundary, daily-report manual/credit-note return treatment, serialization of manual returns against pending/in-flight credit notes, and the identified table-state defects. Do not add production code or tests as part of this specification stage.
- **Schema/dependency policy:** no additional schema migration is required by this revised design. The implementation depends on fiscal/return fields and the partial unique index present in the current working-tree schema/migration delta on `feat-nota-credito`; do not represent these as base-branch fields. Use PostgreSQL row locking for cross-kind return serialization.
- **Out of scope:** partial credit notes, manual-return redesign beyond serialization/report inclusion, changing paid-sale semantics, credential storage/decryption or AFIP transport redesign, and an in-product manual ARCA reconciliation/editor for an AFIP-success/PostgreSQL-persistence-gap case.

Its document filter currently uses only `Order.billType`; for the invoice token it includes A/B/C but still excludes a legacy row with `billType = null`.

Historical JSON can also be an object or serialized JSON; the existing fiscal normalizer accepts `billType`/`afipVoucherType` aliases in this JSON as well as current columns.

It currently exposes `billType` from the nullable column rather than a recovered class. CAE alone proves neither A/B/C nor an AFIP voucher class. The existing QR `qrData` is for printing; no current helper interprets it as a document-type source.

The cashbox is looked up only inside the local finalization transaction, after the external call. Its catch around AFIP currently turns every failure into `REJECTED`, including outcomes where an upstream timeout/invalid response could leave AFIP issuance uncertain. It calls AFIP before saving the response to `SaleReturn`; a local transaction failure after AFIP success therefore leaves no durable credit-note CAE on the `PENDING` record and the action currently refuses to resume a pending request.

The partial unique index prevents duplicate credit-note reservations but does not serialize a manual return against an in-flight credit note. Compare against the eventual merge target/database before rollout.

The credit-note action currently admits any authenticated tenant user, and the detail page currently renders `CreditNoteButton` without a role check. The target policy for this feature is therefore **ADMIN only**, enforced both in UI and in the Server Action. Do not infer permission from hidden UI or the broad `assertWritePermission` helper.

11. `package.json` currently includes Vitest and a `test` script, despite the older generic statement in `AGENTS.md` that no test framework is configured. Use the repository's actual Vitest setup and existing test conventions during the later QA stage.
12. In the AFIP billing chain, `createAfipVoucherAction`, `getArcaCredentialsForBilling`, and `getVoucherNumberForActor` are exported from modules with a top-level `"use server"` directive and therefore are callable public Server Actions today. `getVoucherNumberAction` is also a public action used by `BillParametersForm`. The first three currently accept caller-supplied actor context (directly or indirectly); in particular `createAfipVoucherAction` accepts `authenticatedActor`, `getArcaCredentialsForBilling` accepts a business ID via actor, and `getVoucherNumberForActor` accepts role/business. Those values are untrusted when called over the action boundary. The private trusted actor helpers must no longer be exported from a `use server` module; only public wrappers should remain callable and derive context from `auth()`.
13. `getDailyReportAction` is exported through `src/actions/sales/index.ts`, authenticates and scopes by session business, but currently queries only `CREDIT_NOTE` returns with `AUTHORIZED` status. It therefore drops existing `MANUAL_RETURN` rows from report totals/counts. `processReturnAction` creates a manual return and its stock/cash effects in one database transaction but relies on the `SaleReturn` default status (`PENDING`).

The existing partial unique index covers credit-note-to-credit-note races only; it cannot prevent a manual return and new/in-flight credit-note reservation from both passing their respective checks.
15. The `PENDING` credit-note row can support local-only finalization only when its AFIP response was successfully persisted. The current action/UI has no safe mechanism for an operator to enter independently verified ARCA voucher data after the AFIP call succeeded but persisting that response failed. Do not imply that this gap has an in-product recovery path.
16. `updateBusinessArcaData` and `getBusinessArcaData` are also public exports from `src/actions/arca.ts`; both already authenticate and authorize using session role, with ADMIN restricted to the session business and SUPER_ADMIN's existing cross-business management policy. Keep the caller-provided `businessId` as a target-resource identifier only; it must never replace the session actor or bypass that role/tenant check.
17. Final Step 6 billing-configuration finding: `createCreditNoteAction` reserves a `PENDING` `SaleReturn` before calling `createAfipVoucherAction`, but the latter performs its `requireFeature("hasAfipBilling")` check, tenant credential lookup, point-of-sale/voucher validation and `getVoucherNumberForActor` preflight only after the reservation. These checks can fail deterministically without an issuance request, yet the credit-note action currently treats a generic error result as ambiguous and leaves the reservation pending. The actual feature source is `Business.features` → the related `BusinessFeatures.hasAfipBilling` database field (`prisma/schema.prisma`); `getUserById` includes `business.features`, `auth.ts` copies it into the JWT-backed session, and `requireFeature` reads `actor.business.features`. Note that `requireFeature` deliberately returns success if business/features are absent (its bare-session fallback), so a missing session snapshot is not positive proof of enabled billing and must not be used as the authoritative credit-note preflight. The credit-note flow must move these deterministic eligibility/configuration checks ahead of reservation; error strings from the current public issuance action do not prove whether issuance was reached.

## Functional requirements

### 1. Paid-sale search and legacy fiscal document classification

`searchBill` must continue listing only paid (`paidStatus = pago`) orders for the authenticated business. If a document-type filter is selected, it must recognize both current and recoverable historical document classes before applying page size. All current seller, payment-method (either payment field), inclusive date, document type, business isolation, deterministic ordering, cursor and visual paging behavior must remain in force.

#### Classification contract

Use one server-side, pure classification rule shared by the query filtering and any recovered type exposed by `mapOrderToBillState`:

| Source | Read/mapping | Classification rule |
|---|---|---|
| `Order.billType` | Exact persisted values `Factura A`, `Factura B`, `Factura C`, or `Remito` | An explicit supported type is a candidate. If independent fiscal metadata conflicts with it, classify as `UNKNOWN` rather than silently selecting a value. |
| `Order.afipVoucherType` | Supported AFIP original-invoice codes: `1 → Factura A`, `6 → Factura B`, `11 → Factura C` | Recovery source when `billType` is null/missing, subject to CAE evidence and no conflicting supported type. Other codes are not invoice classes. |
| `Order.CAE` JSON | Accept Prisma JSON object and serialized JSON object as supported by existing `parseCAE`/normalizer. Read `CAE`/`cae` as authorization evidence, and `billType` and/or `afipVoucherType` as type metadata where present. Existing fiscal metadata aliases may be reused: voucher `afipVoucherType`; type `billType`. | With null/missing column `billType`, a valid persisted CAE plus a supported, internally consistent type/voucher code recovers A/B/C. CAE JSON containing just a CAE, number, QR or point of sale does **not** distinguish A/B/C. Do not decode `qrData` to guess a class. |
| Unsupported, missing, invalid or conflicting evidence | Any combination not meeting the rules above | `UNKNOWN`; do not mislabel as invoice or remito. |

For purposes of this search, “valid CAE evidence” means a non-placeholder, non-empty 14-digit CAE value from the persisted CAE field (using the established CAE parser/normalizer rules). Type recovery does not require all fields needed to issue a future credit note; invoice number and point-of-sale completeness remains the separate credit-note eligibility check.

`REMITO` classification must not be inferred from absence of CAE. It requires an explicit persisted `billType = "Remito"` and no positive/conflicting official fiscal evidence. An order with no document filter remains included if it meets the other active filters, even when its document class is `UNKNOWN`. With an active document filter, `UNKNOWN` rows match neither Facturas nor Remitos.

The existing `FACTURA_C` request token remains accepted as a compatibility alias for all three invoice classes. `FACTURA` if emitted by current/future callers has the same meaning. No change to initial filter defaults is required by this feature.

#### Filtering and pagination contract

- Never query one raw page and then discard legacy matches in a way that creates short pages or hides later matching records. Document classification must be applied before returning the logical `take` page.
- Prisma scalar predicates for business, paid status, seller, payment and dates remain server-side. If JSON metadata cannot be expressed reliably in a Prisma PostgreSQL predicate, scan candidate orders in bounded batches using the existing stable `(date desc, id desc)` order and composite cursor, classify candidates server-side, and continue until `take + 1` matches or candidates are exhausted. Do not make an unbounded all-sales fetch or move filter application into the browser.
- The response remains `{ sales: BillState[]; nextCursor: string | null }`. `nextCursor` resumes strictly after the last returned match in the same filtered dataset. A subsequent page must not omit a matching row merely because nonmatching/unknown candidates were scanned. Existing payment/date/seller predicates and cursor must be applied on every batch.
- Preserve the current maximum `take`, `take + 1` detection, `date desc, id desc` ordering, paid-only predicate, business isolation and safe empty response on unauthenticated/failed lookup.
- Recoverable invoice classes must be mapped consistently into returned `BillState.billType` when the persisted `billType` is null; do not alter the CAE parser, print contract, invoice number/point-of-sale mapping, returns, fiscal diagnostics, or eligibility by virtue of this display classification.

### 2. Credit-note preflight, AFIP boundary and reconciliation

All checks which can establish that the operation must not proceed must occur before the irreversible `createAfipVoucherAction` call. Keep the partial unique per-order credit-note reservation for same-kind races and serialize credit-note reservation against manual returns with a database row lock (contract below).

#### Permission and eligibility checks before reservation/AFIP

Every public Server Action in the feature's sales/ARCA billing call chain must authenticate inside the action and derive trusted actor identity (`role`, `businessId`, `userId`) only from `auth()`; never accept, merge, or trust caller-supplied actor context. This includes `createCreditNoteAction`, `createAfipVoucherAction`, public `getVoucherNumberAction`, report/return actions, and the public ARCA configuration actions `updateBusinessArcaData` / `getBusinessArcaData`. Those two ARCA management actions may accept a target `businessId`, but authorization must use the session role and restrict ADMIN to its session business (preserving the existing SUPER_ADMIN management policy). `createAfipVoucherAction` must ignore/reject a forged `authenticatedActor` field rather than use it; tenant credentials and configured point-of-sale lookup must use the authenticated session's business. `getVoucherNumberAction` must retain its public two-argument request contract, authenticate and enforce its existing billing role policy from the session. Move trusted-actor variants of credential and voucher lookup into private server-only helpers (not exported from a `"use server"` module); internal calls may pass a session-derived actor only across this private boundary. `getArcaCredentialsForBilling` and `getVoucherNumberForActor` must no longer be public Server Actions. Do not return credentials to the browser. The credit-note mutation separately requires `role === "ADMIN"`, derives business/user from session, and looks up the order by both `id` and `businessId`. Use the same ADMIN policy in detail-page button visibility. Unauthenticated, forged-actor, and cross-tenant attempts fail closed; non-ADMIN credit-note attempts fail before protected writes or external AFIP calls, while other billing actions retain their existing session-derived role policy. Do not grant `SUPER_ADMIN` for this tenant-scoped credit-note operation; retain only the verified per-action billing policy for ordinary invoice-number/billing access.

Before reserving a new credit note or calling AFIP, re-check on the server:

1. The order exists in the actor's business and `paidStatus === "pago"`.
2. Fiscal normalization returns an unambiguous valid original invoice: CAE, supported bill type A/B/C, compatible original voucher code 1/6/11, positive invoice number and point of sale. User-supplied recovery fields may fill only the already supported missing type/number/point fields; they never supply or replace the CAE or override conflicting persisted values.
3. Full-return content is valid: positive order total, at least one item, and every item has a product ID and positive quantity. The request is a complete reversal only.
4. No credit note is already authorized or unresolved. Existing `CREDIT_NOTE/PENDING` is either safely resumable under the reconciliation rules below or blocks a fresh AFIP request. A different idempotency key cannot create a second return.
5. No existing non-rejected manual return has already reversed/refunded any part of this full-order sale. Because this action restores every original item and debits the full order total, any `MANUAL_RETURN` with status `PENDING` or `AUTHORIZED` makes the full credit-note operation ineligible; a rejected manual row has no committed reversal effects and does not block. Do not double restore stock or cash. Also serialize this decision against concurrent return creation: a preflight read alone is insufficient.
6. An `OPEN` `CashboxSession` exists for the authenticated `userId` **and** `businessId`; use its `cashboxId` for the later cash debit. If not, return a clear eligibility error before creating the `PENDING` reservation or calling AFIP.
7. AFIP billing is enabled and the server has a valid, complete configuration for this exact authenticated business and requested credit-note voucher before creating or claiming a `PENDING` reservation. The authoritative feature flag is the persisted `Business.features.hasAfipBilling` (`BusinessFeatures.hasAfipBilling`) value, not caller input and not a missing/incomplete session feature snapshot. Required business ARCA fields (`cuit`, `cert`, `key`), configured POS membership in `Business.ptoVenta`, credit-note voucher-type/POS validation, and deterministic issuance prerequisites (including required server access/internal configuration and a successful last-voucher-number preflight) must be checked before reservation. Do not reserve a credit note and then discover one of these deterministic failures inside `createAfipVoucherAction`.

Continue to reject unsupported product/content/fiscal state without side effects. Re-check that a valid open cashbox session exists in the local finalization transaction because it may close while AFIP is processing. If it closed after a successful AFIP response, preserve the response and pending reservation; do not mark the credit note rejected or call AFIP again.

#### Required local/AFIP state machine (no additional schema change)

Use existing `SaleReturn` fields and these semantics:

1. **Preflight and serialized reservation:** authenticate/authorize and validate the sale/fiscal/content/cashbox and AFIP-billing eligibility/configuration before any new reservation or retry claim. Resolve the fresh persisted `Business.features.hasAfipBilling` for the session business; fail closed when the business/feature record or flag cannot be established. Validate the `Business` row's required ARCA credentials/CUIT and configured POS, the derived credit-note voucher type and POS, required server-side access/internal configuration, and last-voucher-number preflight. A disabled feature or any deterministic configuration/preflight failure returns an ineligible/configuration result with no credit-note reservation write and no `createVoucher` issuance request. In a short Prisma transaction, acquire a PostgreSQL row lock on the tenant-scoped order row with a parameterized query equivalent to `SELECT "id" FROM "Order" WHERE "id" = $1 AND "businessId" = $2 FOR UPDATE` (using `tx.$queryRaw`/`Prisma.sql` or an equivalently robust database mechanism; do not interpolate user input into raw SQL), then re-read its returns after obtaining the lock. Re-check that there is no `MANUAL_RETURN` in `PENDING`/`AUTHORIZED` and no existing authorized/pending credit note; create a new reservation or conditionally claim a definitively rejected reservation under this same lock. Store reservation as `PENDING` with original voucher, `creditNoteBillType` and `creditNoteAfipType`. Do not reserve before a known missing-cashbox/ineligible result. Release/commit the lock before calling AFIP. Keep the existing unique partial index as the final same-kind constraint.
2. **AFIP call:** only the request that owns a newly reserved row may make the AFIP request. An existing pending request is never blindly reissued.
3. **Definitive rejection / proven no issuance:** mark `REJECTED` only for an authoritative AFIP rejection, or a deterministic pre-issuance failure for which the server can prove the `createVoucher` issuance request was never invoked. The preferred design is to identify and return feature/credential/POS/voucher/access/last-number configuration failures before reservation. If a race or other condition nevertheless surfaces such a failure after reservation, only a structured trusted server result with an explicit pre-issuance phase / `issuanceNotStarted` guarantee may release the reservation to `REJECTED`; never infer this from error text, HTTP status alone, or a caller-controlled diagnostic. Preserve the same-key retry policy only for this definitive non-issuance state, subject to re-running every preflight check. Never classify a timeout, connection reset, process interruption, ambiguous/malformed response, or missing response fields as a definitive rejection.
4. **AFIP success captured:** validate the response (14-digit CAE and positive number/point of sale) and durably persist `creditNoteCAE`, `creditNoteNumber`, `creditNotePointOfSale` on the existing `PENDING` `SaleReturn` before attempting inventory/cash/order-local finalization. A response that does not prove success or non-issuance is ambiguous: leave the row `PENDING`, write a safe reason, return a pending/reconciliation result, and do not automatically invoke AFIP again.
5. **Atomic local finalization:** in one Prisma transaction, conditionally claim the pending row and set `AUTHORIZED`, `authorizedAt`, retaining its persisted voucher fields; create all `SaleReturnItem` rows; restore each product quantity; create matching RETURN `StockMovement` rows; decrement the active session's cashbox by the full order total; and create the negative `CashMovement`. Any failure rolls back **all** these local effects and the status transition, while the already saved AFIP response remains on the pending row outside that transaction.
6. **Safe local resume:** if a pending `CREDIT_NOTE` already has a complete, valid persisted voucher response, the same action may resume **only local finalization**, after permissions, order eligibility and open-cashbox checks. It must not call AFIP again. Retain the existing explicit admin affordance only for this actionable saved-response case. Pending requests without saved success data remain non-actionable and display “pending / reconciliation required.” The UI/response must distinguish “safe to finalize locally from saved AFIP response” from “AFIP outcome unknown; do not retry.”
7. **Unavoidable persistence-gap failure (manual ARCA reconciliation is not implemented):** if AFIP may have issued a voucher but writing its response to PostgreSQL fails, retain the reservation as `PENDING` (never mark `REJECTED`, never retry AFIP automatically), return a safe reconciliation-required result, and log the order/return/business IDs and phase without secrets or raw credentials. The current schema cannot atomically commit an external AFIP action with PostgreSQL. There is no current safe in-product UI/action to enter independently verified voucher metadata or resolve such a row; this feature does not implement one. Do not claim that an ADMIN can recover this case through the credit-note UI, or that saved-response local resume handles a response-persistence gap. Operations must fail closed and escalate through a separately approved, audited operational procedure outside this feature. Any future in-product/manual ARCA recovery requires a separate security, audit, and idempotency design.
8. **Terminal result:** return success only after the transaction commits with `AUTHORIZED` and complete voucher metadata. If another request already finalized, return the existing authorized result when it is the same logical credit note; otherwise return conflict. Cache revalidation/refresh errors must not undo or misreport a committed fiscal/local result.

`processReturnAction` must use the same tenant-scoped `Order FOR UPDATE` lock inside its existing transaction before reading return state and must hold it through manual return record/effect creation and commit. After acquiring it, reject a new manual return if an authorized or pending `CREDIT_NOTE` exists; rejected credit-note reservations do not block a manual return. The credit-note reservation transaction uses the same lock and checks for existing `MANUAL_RETURN` rows in PENDING/AUTHORIZED. This creates a deterministic winner: if the manual-return transaction commits first, credit-note reservation observes that return and makes no AFIP call; if the credit-note reservation commits first, the manual return observes its pending reservation and rolls back without effects. Keep the lock scoped to the order/business and avoid taking it while waiting on AFIP. If a locking implementation uses a transaction isolation level that can surface serialization errors, retry or safely return a conflict without side effects. The row lock is the concurrency authority across return kinds; the partial unique index and conditional status update remain authorities for same-kind credit-note invariants. Never call AFIP from inside a long-running Prisma transaction or use a local process lock as the database concurrency authority. Keep user-facing error strings safe; logs may contain phase/status/IDs and boolean-presence diagnostics, but not credentials, internal keys, or raw AFIP response bodies.

#### Daily-report return treatment

Continue reporting all qualifying manual-return activity while adding credit-note rows. A `MANUAL_RETURN` created by the existing flow has its stock/cash effects committed in the same transaction as its return row and retains the default `PENDING` status; therefore include `MANUAL_RETURN` rows with status `PENDING` or `AUTHORIZED` in daily/periodic report return totals and `returnCount`, and exclude `REJECTED`. For credit notes, include only `CREDIT_NOTE` rows with status `AUTHORIZED`; exclude `PENDING` (including saved-response/not-yet-finalized and unknown-outcome rows) and `REJECTED` to avoid recognizing uncommitted local reversal effects. Partition by `kind` explicitly so a pending credit note is never counted as a manual return. Use the same date/business filters for both kinds and include each return row exactly once in `totalReturns` and `returnCount`.

### 3. Permission visibility

- On `src/app/(protected)/sales/[id]/page.tsx`, render `CreditNoteButton` only for `ADMIN`, matching the existing sale edit/detail management policy. Keep fiscal diagnosis and already-issued credit-note status readable to other authorized business users unless current product policy says otherwise.
- In `createCreditNoteAction`, enforce the same role before database reservation or AFIP interaction. Return a typed forbidden/unauthorized failure with no side effects for every non-ADMIN actor.
- The UI gate is not security; direct Server Action tests must establish server enforcement.
- Do not use `ADMIN_EMAIL`/email as a substitute for role authorization. Do not silently add `SUPER_ADMIN` to this business-scoped permission.

### 4. Remove no-op filtered-sales alias

Remove `SalesTable.filteredSales` and its identity `useMemo`. Derive totals, `totalPages`, and `currentSales` directly from the authoritative `liveSales` state. Keep `liveSales` as the one loaded result set; this must not reintroduce a client-side copy of the server document filters.

### 5. Isolate load-more responses from refresh generations

Treat filter replacement, initial-query replacement and each Pusher refresh as a new dataset generation. A load-more request captures both that generation and its cursor/filter snapshot. It may append sales, update cursor/`hasMore`, or clear its loading state only if it still owns the current generation/request. Starting a replacement invalidates earlier page requests and clears the old generation's loading indicator; an old request's `finally` must not clear loading for a newer request. Preserve ID deduplication and the latest dataset's current page/cursor/filters. Do not allow a response from the old page to append, overwrite cursor/`hasMore`, or mutate state after Pusher has replaced the dataset.

## Interfaces and data contracts

Existing `GetSalesParams`, `SalesFilters`, and `GetSalesResult` wire contracts remain unchanged except accepting the already documented `FACTURA` canonical token in addition to the legacy `FACTURA_C` token, if the implementation chooses to emit it. Classification is an internal server contract:

```ts
type SalesDocumentClass = "INVOICE_A" | "INVOICE_B" | "INVOICE_C" | "REMITO" | "UNKNOWN";
```

It is produced only from persisted order data and is not accepted from the browser. In a recovered historical invoice, mapping to `BillState` uses the resolved canonical label (`Factura A|B|C`) while retaining all existing `CAE`, `ptoVenta`, original-voucher, return and client fields.

The credit-note action result should distinguish at least: success, forbidden, ineligible, definitive AFIP rejection, conflict/already authorized, ordinary unresolved pending, and reconciliation-required pending. The response must expose no secret or raw upstream payload. For safe local-finalization recovery, expose only whether the persisted response is complete/actionable (and the necessary existing display metadata), not trust a CAE supplied by the browser. Public AFIP invoice/voucher actions derive actor context from the session, not request fields. Internal credential/voucher helpers are server-only and unavailable as public Server Actions. Manual ARCA response-entry/reconciliation is not an interface in this feature.

No additional Prisma changes are needed by this specification: current-tree `SaleReturn` fields store a returned CAE/number/POS before local finalization and `reason` can identify the unresolved phase; PostgreSQL row locks serialize return kinds without a new column. No new status enum is proposed. This does **not** mean the current schema matches an older baseline: the checked-in/current migration history includes fiscal and return metadata plus the partial index listed in Repository findings. Implementation/release must include and validate those current-branch migrations against the deployment target; do not assert that they are baseline or already deployed without checking branch diff and database migration state.

## Files and responsibilities

### Required implementation files

- `src/actions/sales/get-sales.ts` — preserve paid-only/tenant/filter/cursor semantics; classify legacy/null bill types before logical pagination; scan candidate batches if needed for JSON metadata; preserve compatible filter tokens.
- `src/services/afip/credit-note.ts` or a narrowly scoped new pure sales-document classification module — centralize reliable document type recovery / conflict rules. Reuse CAE validation where appropriate; do not parse QR URLs or duplicate divergent query/UI rules.
- `src/actions/sales/history.ts` — align returned `BillState.billType` with the same resolved fiscal class for historical null rows without changing the credit-note eligibility contract; retain session business isolation and include manual returns under the stated kind/status rules in daily/periodic reports, alongside only authorized credit notes.

## Measurable acceptance criteria

### Sales history / parity

1. `getSalesAction` never returns an order whose `businessId` differs from the authenticated business or whose `paidStatus` is not `pago`, with filters empty or active.
2. With the invoice filter active, paid records with persisted A/B/C `billType` values all match; paid historical records with `billType = null`, valid CAE evidence, and supported `afipVoucherType` 1/6/11 match as A/B/C respectively.
3. The same recovery works when supported `billType`/`afipVoucherType` metadata is present in a valid historical CAE JSON object (including serialized JSON accepted by the existing parser), even when nullable scalar `billType` is null.
4. A valid CAE with no supported class metadata, invalid/placeholder CAE, unsupported voucher code, or conflicting type sources is not guessed into an invoice class. An explicitly typed remito with no contradictory official fiscal evidence matches Remitos; a CAE alone or conflicting fiscal row does not get mislabeled as a remito.
5. With no document filter, every paid row matching remaining filters remains eligible for results, including `UNKNOWN` legacy rows. With a selected type filter, `UNKNOWN` rows match neither class.
6. Filtering continues to match either `paymentMethod` or `paymentMethod2`, inclusive date bounds, seller, and the same filter snapshot across all cursor batches. The type-filtered logical first page is filled with matching rows when later raw candidates match; classification-after-a-single-page must not create a short page or hide those rows.
7. Iterating all result cursors over a fixture with at least 250 paid rows and at least 30 historical null-`billType` recoverable invoices returns each matching ID exactly once in stable `date desc, id desc` order. Same-date IDs retain deterministic ordering. `nextCursor` is null exactly when there is no further matching row.
8. `FACTURA_C` remains a backward-compatible alias for all A/B/C; `FACTURA` if accepted/emitted has identical semantics. Existing Remito/payment/date/seller selections remain as displayed.
9. Search table/print mapping for a recovered legacy invoice retains the CAE, resolved `billType`, point of sale/document number where available, and existing return/credit-note metadata. A field needed for display does not become sufficient proof of credit-note eligibility.
10. The same shared implementation and fixture outcomes apply in development, main and production; there is no environment-dependent branch. Before rollout QA compares the behavior against the available main/production baseline. The working repository contains no second production-specific implementation to update.

### Credit-note safety / permission

11. Every public action in the feature's AFIP billing chain authenticates from the current session and derives business/user/role exclusively from that session. Passing forged `{ authenticatedActor: { role: "ADMIN", businessId: anotherTenant, ... } }` to `createAfipVoucherAction`, or forged ADMIN/tenant context to any public helper-shaped input, cannot select another tenant's credentials, point-of-sale configuration, or voucher number. Unauthenticated direct calls fail closed. `getArcaCredentialsForBilling` and `getVoucherNumberForActor` are no longer public `use server` exports; internal trusted helpers live in server-only non-action code. Public `getVoucherNumberAction` retains its two numeric arguments and session authorization.
12. A non-ADMIN user can neither see the actionable credit-note button nor invoke `createCreditNoteAction` successfully. Direct calls with a forged ADMIN actor/business field return forbidden/unauthorized with zero SaleReturn writes and zero AFIP calls; ADMIN can use the eligible flow. SUPER_ADMIN remains denied under the checked-in sale policy.
13. A missing, closed, wrong-user or wrong-business cashbox session fails before creating a new credit-note `PENDING` row and before calling AFIP. A valid session is selected by session `userId` and `businessId` and is rechecked before local cash finalization.
14. Unpaid, cross-business/not-found, invalid fiscal, conflicting fiscal, incomplete item/product, nonpositive total, already authorized/pending, or previously reversed by a `MANUAL_RETURN/PENDING` or `/AUTHORIZED` record make no new AFIP call. A rejected manual return does not count as a committed reversal. A pending credit-note request with no persisted AFIP success data never triggers an automatic second AFIP request.
15. A deterministic two-transaction race test makes a manual return and credit-note reservation contend on the same tenant-scoped order row lock. If the manual-return transaction commits first, reservation observes the manual return and makes no AFIP call. If the credit-note reservation commits first, the manual return observes the pending reservation and rolls back with no return row/items, stock movement/product increment, cash debit or cash movement. No schedule permits both operations to commit. Same-kind concurrent credit-note requests remain limited to one AFIP call by the partial unique index and conditional claim.
16. A definitive AFIP rejection or trusted proof that the issuance request was never invoked is recorded `REJECTED`; an ambiguous timeout, connection/process failure, malformed/missing-success data, or response-persistence failure is not `REJECTED`, remains `PENDING`, returns a reconciliation-required result and cannot be retried against AFIP automatically.
17. On valid AFIP success, all three response fields (CAE, number, point of sale) are persisted on the `PENDING` row before local finalization begins.
18. If any local finalization step fails, the transaction leaves no partial stock increments, RETURN stock movements, return items, cashbox debit, cash movement or `AUTHORIZED` status; the separately saved AFIP response remains on `PENDING`.
19. Re-invoking the action for a pending row with complete valid response metadata finalizes locally exactly once, does not call AFIP, does not duplicate stock/cash/return-item effects, and marks the row `AUTHORIZED` only with all local effects committed. A missing/closed cashbox blocks local finalization but preserves the saved response for later safe completion.
20. A pending row without persisted voucher response is visibly differentiated as unresolved/possibly issued; a pending row with a complete persisted response offers only safe local finalization. The UI never provides an AFIP reissue action. Response-persistence failure has no in-product manual ARCA data-entry/reconciliation path in this feature; it stays blocked and is escalated outside the product.
21. Successful finalization returns success only after atomic local commit; later revalidation/refresh failure cannot change the success result. Existing authorized response replay remains idempotent.
22. Daily and periodic reports include each `MANUAL_RETURN` once when status is `PENDING` or `AUTHORIZED`, exclude `MANUAL_RETURN/REJECTED`, include each `CREDIT_NOTE` once only when `AUTHORIZED`, and exclude pending/rejected credit notes. Totals/counts apply the same business/date window, and a pending credit note is not counted as a manual return.

### Table state

23. The `filteredSales` identity memo is removed; totals, page count and current rows use `liveSales` directly and produce the same visible results for a fixed dataset.
24. In a deterministic deferred-promise test, start load-more, trigger a Pusher first-page refresh, resolve the old load-more afterward, and verify that the new dataset, cursor, `hasMore`, page and totals contain no old-page append or stale overwrite.
25. If another load-more request belongs to the refreshed generation, the old request's `finally` cannot clear the newer loading state. Filter changes, initial replacement, and Pusher refresh invalidate all previous-generation writes; ID dedupe and existing page navigation remain intact.
26. Deterministic AFIP billing-ineligibility/configuration failures are detected before credit-note reservation and issuance. In particular, when persisted `Business.features.hasAfipBilling === false`, a direct ADMIN request produces zero `SaleReturn` creates/updates and zero `createVoucher` issuance calls; missing tenant CUIT/cert/key, absent or invalid configured POS, incompatible credit-note voucher type, missing required server billing configuration, and failed/invalid last-voucher preflight likewise create no new/claimed reservation and make zero issuance calls. Tests assert the feature result comes from the actual tenant configuration source (`Business.features.hasAfipBilling`), not browser input or a missing session feature snapshot. A trusted post-reservation no-issuance result is acceptable only if structured and produced by server code that guarantees the issuance call was not started; free-form errors/statuses are insufficient. By contrast, a network/ARCA result whose issuance outcome is uncertain remains `PENDING`, reconciliation-required, and cannot invoke issuance on retry.

## Explicit non-goals / architectural decisions

- No additional schema changes: the current working-tree migration chain already contains fields/indexes this feature depends on; verify its branch delta and deployment state. The current pending `SaleReturn` can persist a confirmed response only if that response write succeeds.
- Do not mark an uncertain external outcome `REJECTED`; that could allow a duplicate fiscal issuance.
- Do not claim a database transaction can cover AFIP and PostgreSQL atomically. If voucher response persistence fails, stay pending and fail closed; manual ARCA reconciliation/data entry is not implemented in this feature and must not be presented as a safe UI recovery capability.
- Serialize manual-return and credit-note workflows by locking the same tenant-scoped order row; a unique index alone is not sufficient for this cross-kind invariant.
- Do not infer A/B/C from CAE presence, a default bill type, invoice number, or `qrData`.
- Do not relax tenant isolation, paid-only history, cursor ordering, sale role restrictions, or cashbox ownership validation.
- No dependencies or secrets are introduced.
