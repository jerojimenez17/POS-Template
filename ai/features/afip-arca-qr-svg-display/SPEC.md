# AFIP/ARCA invoice QR missing from print/render

## Status and scope

- **Status:** Architecture/root-cause specification updated with user-provided production evidence. This task changes only this specification; no implementation or tests are changed. Repository-wide G4 remains **not passed / blocked** as recorded in `TEST_CHECKLIST.md`; this specification update is not new G4 verification.
- **Symptom:** AFIP invoice issuance and sale persistence now succeed, but the invoice print/render does not show its QR SVG.
- **Scope:** Ordinary A/B/C sale invoices, covering gateway response parsing, QR grant creation and consumption, `Order.qrDataPolicyVersion`/grant-reference persistence, tenant-scoped print-data resolution, and the SVG/PDF/thermal receipt paths. Also includes the narrowly scoped issuer-CUIT normalization needed for partial-payment QR print URL construction.
- **Out of scope:** Changing QR trust policy, trusting browser-supplied QR values, reissuing/reconciling an invoice, broader partial-payment voucher behavior, changing fiscal payload semantics, or applying a database migration as part of this specification-only task.

## Governing trust contract

The existing `ai/features/afip-arca-qr-data/SPEC.md` remains authoritative:

- New invoice writes use policy version `1`, whether or not an attestation grant is available.
- A new invoice QR is printable only when the order references a valid `AuthorizedArcaQrGrant` bound to that invoice and tenant.
- Only migrated policy version `0` rows with no grant may use the database-persisted legacy raw QR. Version `1` with no valid grant resolves to no QR.
- Browser-provided `qrData`, `qrUrl`, payload, and request date are never authorities. A missing or invalid QR proof must not prevent an authorized CAE from being saved or printed as an invoice.

This feature must preserve that contract. It must not add a client fallback, reinterpret a new row as historical, or make CAE props/state an alternative QR source.

## End-to-end repository findings

### 1. AFIP response and grant creation

1. `src/services/afip/voucher-response.ts` parses the supported AFIP response shapes. `qrData` is retained only as a non-empty string and is internal response data; it is not itself proof for a new invoice.
2. `src/lib/server/afip-voucher.ts` handles parsed CAE success. For standard invoices it builds the product QR payload from server-side request/fiscal context, takes raw QR only from the parsed gateway response, and calls `createAuthorizedArcaQrGrant`.
3. `src/lib/server/authorized-arca-qr-grant.ts` validates the claims, creates a random opaque bearer token, and persists only its SHA-256 hash with the invoice bindings/claims. Invalid claims or a persistence error yield no grant/token and are deliberately non-fatal to the authorized CAE.
4. `src/actions/afip.ts` returns the opaque `qrAttestationToken` in its public DTO, not the raw QR/payload/URL. `BillButtons.tsx` places this token on the in-memory CAE solely for save.

**Implication:** An AFIP success is not evidence that a QR grant was created. A successful invoice with no token is an explicitly supported outcome. QA confirmed two input shapes that can stop issuance before a grant/QR becomes available (formatted Business CUIT and the narrowly defined consumer-final empty-document-type projection); those are separate input blockers and are not the root cause established for the incident below.

### Confirmed QA input blockers for grant/QR eligibility

1. **Formatted Business/issuer CUIT:** `ArcaFieldsSchema` permits a visually formatted CUIT, while QR payload construction and grant validation require the 11-digit identifier. Normalize non-numeric separators from the tenant Business CUIT to its digits for QR payload construction and QR issuer validation. Accept only a result of exactly 11 digits; otherwise reject QR payload/grant eligibility. This normalization is local to the QR path: do not rewrite tenant identity (`businessId`), Business data, AFIP credential values, or the outbound AFIP wire/request. Apply the same digits-and-length rule when constructing the partial-payment print QR URL from that payment's Business.
2. **Consumer-final BillParametersForm shape:** `BillParametersForm` can pass `clientDocumentType: ""` with `clientDocumentNumber` absent. `createAfipInvoiceDTO` currently rejects the empty type before voucher preparation/issue. Normalize `""` to absence only when the recipient condition is `Consumidor Final` and there is no document number; the resulting QR mapping is `tipoDocRec: 99`, `nroDocRec: 0`. Do not generalize empty-type acceptance to identified recipients or other IVA conditions, and do not infer consumer-final status solely from a blank type.

The RED acceptance evidence is `ai/features/afip-arca-qr-svg-display/issued-voucher-to-print.integration.test.ts` (formatted issuer/tenant CUIT end-to-end and BillButtons consumer-final DTO projection) and `ai/features/afip-partial-payment-voucher/payment-voucher.contract.test.ts` (partial-payment QR with formatted Business CUIT). These tests exercise the branches that previously prevented QR grant/URL availability; they do not establish why a particular invoice already persisted without a visible QR.

### 2. Sale save, grant consumption, and policy persistence

1. `src/components/Billing/BillButtons.tsx` calls `createAfipVoucherAction`, then `processSaleAction` with the CAE and opaque QR token. It waits for the returned persisted `orderId` before creating the immediate-print snapshot.
2. `src/actions/sales/process.ts` attempts to consume the token inside the order transaction using tenant, CAE, invoice type/number/POS, total, issuer CUIT, and recipient bindings. The QR fields supplied in the request are not copied into `Order.CAE`.
3. Only a successfully consumed grant contributes `qrAttestationId` to `Order.CAE`. The same write explicitly sets `qrDataPolicyVersion: 1` whenever CAE is saved. Missing, invalid, expired, consumed, or mismatched proof does not make CAE save fail, but it leaves no grant reference.
4. `src/actions/sales/update.ts` applies the analogous version-1 and grant-consumption behavior for CAE added to an existing order.

**Implication:** The prior Prisma persistence fix proves at most that order creation now succeeds. It does not prove that the optional QR token was issued, accepted/consumed, or linked on the saved order. A version-1 order without `CAE.qrAttestationId` is intentionally not printable with QR.

### 3. Authorized print-data resolver

1. `src/actions/sales/qr-print.ts` exposes `resolveOrderQrPrintDtoAction(orderId)` as a Server Action.
2. `resolveOrderQrPrintDto()` in `src/lib/server/authorized-arca-qr-grant.ts` derives the tenant from `auth()`, loads the tenant-owned order, and applies the policy gate:
   - version `0` and no grant reference: persisted legacy raw only;
   - version `1` and grant reference: load the same-tenant grant and check CAE/invoice/tenant and related persisted bindings, then return a rebuilt verified URL or that grant's raw fallback;
   - all other cases: `{ qrValue: null, qrKind: "none" }`.

The resolver returns `none` for absent or mismatched grant references, binding mismatches, missing grant records, or unverifiable URL/raw data. That suppresses new QR without suppressing invoice content.

### 4. Render paths and SVG generation

- **Immediate invoice print:** `BillButtons.tsx` strips the opaque token from the print-only CAE props, empties `qrData`, and supplies the persisted order ID in the print snapshot. This is the correct trust boundary. `PrintableTable.tsx` resolves QR by that persisted ID and waits for resolution before responding to a print trigger. It does not render a QR from the pre-save authorization response.
- **Visible/print banner and thermal receipt:** `PrintableTable.tsx` conditionally mounts `QRCodeSVG` only when its server-resolved `serverQrValue` is truthy. Thermal printing receives the same resolved value.
- **Immediate PDF:** `PrintableTable.tsx` creates SVG text with `QRCode.toString(serverQrValue, { type: "svg", ... })`, makes a data URL, and passes it to `buildPDFHTML`.
- **Historical/reprint actions:** `PrintOptionsPopover.tsx` resolves the persisted order QR before generating PDF or thermal output. `src/lib/print/BrowserPrint.ts` generates the thermal image from the supplied resolved print value; `src/lib/print/pdf-templates.ts` inserts a validated image data URL.
- **Partial payment receipt:** This is a separate authority/path and is not a candidate cause for an ordinary sale invoice. It must remain isolated from `Order.CAE`.

All ordinary invoice paths therefore share a common prerequisite: the print DTO must contain a non-empty `qrValue`. The SVG/PDF/thermal generators do not fetch grants or decide trust. If the server DTO is `none`, an empty print value, or a failed lookup, omission is expected. If the server DTO contains a valid non-empty value but no SVG/image is produced, the renderer path is the defect.

## Confirmed production root cause (new Step 1 evidence)

The user supplied consecutive, sanitized runtime events for the affected invoice:

```text
{ stage: 'grant-create', outcome: 'created' }
{ stage: 'save-consume-ref', outcome: 'rejected', reason: 'payload-invalid' }
{ stage: 'resolve', outcome: 'rejected', reason: 'policy-v1-no-ref', qrKind: 'none' }
```

The user also identified the concrete save-path behavior in `consumeAuthorizedArcaQrGrant`: `AuthorizedArcaQrGrant.fiscalAmount` is `Decimal @db.Decimal(12,2)`, but the consumer performs `updateMany` to set `consumedAt` before calling `decimalString(grant.fiscalAmount)`. That helper accepts only `string | number`; Prisma's `Decimal` instance therefore normalizes to `null`. The function then returns `null` after the grant has already been marked consumed. CAE save proceeds under the intentional non-fatal proof policy, but stores no `qrAttestationId`; version 1 consequently resolves to `policy-v1-no-ref` / `qrKind: 'none'`.

**Root cause is confirmed:** the grant is created, rejected during save with `payload-invalid`, and later cannot be resolved because the version-1 order has no attestation reference. The ordering/type mismatch (consumption CAS before exact Decimal normalization/claim parsing) explains all three consecutive observations; this is not an SVG rendering defect and not a failure to create the grant. The events are user-provided, not independently captured by this session; the code/schema facts and the causal sequence described here are the supplied evidence. The user confirms that the prior grant/policy migration is already applied. That migration status is user-confirmed and was not independently queried.

The recovery scope is the already-saved affected invoice only. Do not issue, query, retry, replace, or otherwise re-emit its CAE. A repair may associate an already-consumed orphan grant only under the strict one-candidate/all-bindings/CAS rules below. An ambiguous or mismatched candidate remains unlinked and must resolve to no QR.

## Required fix design

### Normal grant consumption and order linking

1. Convert `fiscalAmount` from Prisma `Decimal` to an exact canonical decimal representation using Decimal operations (not JS floating-point conversion). Validate the complete claims object and all bindings, including this amount, before any state-changing compare-and-set. Reject malformed/unparseable claims without setting `consumedAt`.
2. Keep exact money comparisons in Decimal/canonical decimal space; do not use tolerance comparisons or `Number` round trips. The representational contract is the stored `Decimal(12,2)` amount. Any value that cannot be represented/validated under that contract is rejected before consumption.
3. After every claim is parsed and validated, consume the grant through the existing atomic one-use CAS. Only a successful CAS may return the grant id/claims to the sale flow. A failed CAS returns no proof.
4. In the same interactive Prisma transaction, create the order and then associate the consumed grant with the new order (`orderId`) after `tx.order.create` returns its id. Persist `qrAttestationId` into the order's CAE JSON as part of that same transaction. Any later failure rolls back order, grant consumption/link, and other local sale writes together. `reference-persisted` telemetry, if emitted, is post-commit only.
5. Preserve non-fatal CAE persistence: an absent, invalid, expired, replayed, or mismatched QR token does not fail an otherwise valid authorized CAE save. Such new CAE orders stay policy version `1`, have no attestation reference, and resolve to `none`.

### One-time recovery for the already-affected order

Provide a deliberately one-time, server-side repair procedure scoped to the affected persisted order, not a general resolver fallback or bulk adoption mechanism. It must be authenticated and tenant-scoped and execute in a transaction. Repair is eligible only when the target is a policy-version-1 CAE order with no `CAE.qrAttestationId`, and the candidate grant is already consumed but has `orderId IS NULL`.

The repair must find **exactly one** candidate whose every binding matches the order and its owning Business: tenant/business id; CAE; bill type and AFIP voucher code; point of sale; invoice number; fiscal amount compared exactly as Decimal; issuer CUIT after the same digits-only normalization and 11-digit validation; and recipient IVA condition, document type, and document number (preserving the established null/empty and leading-zero semantics). A missing field, invalid normalization, mismatch, zero candidates, or more than one candidate means no repair and no QR. Do not loosen or skip a binding because it is optional in another path.

For the single fully matching candidate, atomically compare-and-set `orderId: null -> order.id`; require exactly one updated row. In the same transaction, write that grant id as `qrAttestationId` in the order's CAE JSON. If the CAS loses a race, the order update must not commit. The procedure is one-time/idempotent: an already-linked grant/order is not silently reassigned, and subsequent execution cannot link another grant. The normal print resolver remains fail-closed and does not repair records on reads.

### Additive persistence/deployment requirements

- Add `AuthorizedArcaQrGrant.orderId` as nullable and unique, with an FK relation to `Order`; add the corresponding optional relation on `Order`. Existing grants remain null until linked by normal post-create flow or the narrowly scoped recovery. Do not bulk-backfill or guess associations.
- This requires a **new additive migration** because the user confirms the previous migration is already applied. Include nullable column, unique index, and FK; do not edit/rewrite the already-applied migration. The migration is specified but must not be applied in this task. It requires normal deploy-time migration rollout and a generated Prisma Client from the updated schema before application code depending on the field ships.
- Do not weaken legacy/new policy: version `0` with no grant retains only its existing raw legacy path; version `1` with no verified reference remains QR `none`. Do not re-emit CAE, change invoice/fiscal data, or reconstruct QR from browser input.

**Safe investigation/fix order:** use bounded server-side observability for the affected flow without changing QR trust policy or the public print DTO. If QR value is `none`, repair only the proven grant-create/binding/persistence/resolution defect. If a verified/legacy QR value is selected but SVG/PNG generation fails, repair only the renderer path. Resolver diagnostics remain server-only; a separate authenticated outcome-report Server Action is permitted solely for the allowlisted renderer outcome contract below. It must not return `qrKind`, `reason`, diagnostic detail, or QR content to the browser. Do not log raw errors/messages or arbitrary object serialization, as they may include sensitive values.

### Safe diagnostic event contract

- Emit structured, server-side events at the grant-create, save-consume/reference, resolver, and renderer transitions. Every logged field must be a fixed, reviewed enum/category; do not include dynamic identifiers or source values. Do not log `orderId`, `tenantId`, CAE, CUIT, recipient identity/data, bearer token, raw QR, QR URL, payload, fiscal amounts, or any substring/hash/encoding of these values. Do not log request/action bodies, Prisma records, thrown error messages/stacks, or full URLs.
- `stage` is restricted to `grant-create`, `save-consume-ref`, `resolve`, `render`. Record stage outcomes categorically (for example: grant created/rejected; token present/absent, consume accepted/rejected, reference persisted/absent; resolver completed; renderer outcome), not as raw inputs or error details.
- **Commit truth:** `reference-persisted` means the enclosing order transaction committed successfully. Emit it only after the transaction promise resolves successfully and the persisted grant reference is known to be part of the committed write. Never emit it inside the interactive `$transaction` callback. If logging remains inside that callback, it must instead be named `reference-staged` (not `reference-persisted`) and must not be presented as evidence of persistence/commit. A thrown/rolled-back transaction must produce no `reference-persisted` event.
- Resolver `reason`, when a transition is rejected or QR is unavailable, must be selected from this closed allowlist only: `claims-invalid`, `grant-create-failed`, `token-absent`, `binding-mismatch`, `grant-expired/replayed`, `policy-v1-no-ref`, `grant-row-missing`, `issuer-mismatch`, `invoice-binding-mismatch`, `payload-invalid`, `renderer-failed`, `QR-ready`. Do not use arbitrary exception text or append data to a reason. A success may omit `reason`; `QR-ready` is reserved for a verified/legacy non-empty QR selected by the resolver (it does not mean that a renderer succeeded). `qrKind` and `reason` remain internal resolver/telemetry data and are never accepted from or returned to clients.
- Record the selected `qrKind` as one of `verified-url`, `verified-raw`, `legacy-raw`, or `none`, with `none` only when the resolver returns no printable value. When kind is `none`, report the applicable allowlisted rejection reason; when a non-`none` kind is selected, report `QR-ready`. Renderer success/failure is a separate downstream categorical observation, with `renderer-failed` used only for a renderer failure after a non-`none` value was selected.
- Existing `render`/`handoff`/`QR-ready` telemetry is not evidence that SVG/PNG generation or output handoff succeeded: `QR-ready` records resolver selection only. The renderer outcome report and assertions against actual non-empty SVG/PNG output are required to distinguish generated, failed, and submitted states.
- Resolver diagnostics remain exclusively in server logs/approved server telemetry. The public resolver DTO and resolver Action result must not gain a diagnostic field, reason, status, or log data; no resolver diagnostics may be forwarded to the browser. Existing client rendering continues to receive only its currently authorized print DTO/value as required by the established flow. The renderer outcome action below is a deliberately narrow exception: it accepts only `renderer` and `outcome`, and returns only a generic acknowledgement, never resolver or error detail.
- **Authenticated renderer outcome report:** clients may call a dedicated authenticated Server Action after the local renderer/handoff reaches an outcome. Its complete accepted input is exactly `{ renderer, outcome }`, where `renderer` is one of `pdf`, `thermal-html`, `qz`, `partial` and `outcome` is one of `generated`, `failed`, `submitted`. No order/tenant identifier, `qrKind`, `reason`, QR value, SVG/PNG bytes, URL, payload, token, or arbitrary metadata is accepted or sent. Validate server-side against closed enums and reject malformed values, extra fields, and any out-of-allowlist renderer/outcome without logging the submitted values. Authenticate inside the action on every invocation; do not trust page-level/client authentication. Apply bounded request validation (fixed-size enum fields only) and appropriate abuse/rate limiting so the endpoint cannot be used for unbounded log amplification. The response is a generic success/failure acknowledgement only; it must not echo the input or expose a reason.
- The action logs server-side only the fixed `stage=render`, `renderer`, and `outcome` enums (plus a fixed event name if required by the logger). The client reports outcome only, never QR content. `qrKind`/resolver `reason` are independently determined and kept internal; a client report cannot assert or override them. `generated` means a non-empty QR SVG or PNG was actually constructed in the selected output path. `submitted` means the output handoff succeeded at the relevant software boundary (for example, QZ submission/API success), not that a physical printer produced paper. `failed` records a renderer or handoff failure; do not send exception text/reason. These observations are categorical diagnostic reports, not trusted proof against a malicious authenticated client and not a guarantee of physical output.
- These observations support attribution only. They must not change the non-fatal CAE-save behavior, trust policy, output/print behavior, or the generic user-facing fiscal result/error. In particular, QR failures must not become fiscal errors or block authorized invoice persistence.

## Acceptance criteria

- **AC-01 — preserve policy:** Every new CAE order remains policy version `1`, even when QR grant creation, consumption, or lookup fails. Legacy raw QR is accepted only for version `0` with no grant. No client-supplied QR field or `createdAt` fallback can yield a QR.
- **AC-02 — layer attribution:** Focused regression coverage distinguishes grant creation, save-time consumption/reference persistence, resolver output, and SVG generation. A test failure identifies which handoff failed rather than treating “no QR on paper” as one undifferentiated condition.
- **AC-03 — successful proof path and exact incident regression:** Given valid claims whose `fiscalAmount` is a Prisma `Decimal` from `Decimal(12,2)`, normalization occurs before consumption CAS; the transaction saves the order, links the grant's `orderId`, and persists `CAE.qrAttestationId`. The tenant-scoped resolver returns a non-empty `verified-url` or `verified-raw`. The incident's `grant-create:created` → `save-consume-ref:rejected/payload-invalid` → `resolve:rejected/policy-v1-no-ref/none` sequence is covered and no longer occurs for this valid fixture.
- **AC-04 — no-proof path remains safe:** Given missing/invalid QR proof or a binding mismatch, the authorized CAE/order save succeeds under existing behavior with policy version `1`, no QR grant reference/claims from the client, and resolver result `none`; every invoice renderer omits the symbol while retaining invoice/CAE content and completing print/export.
- **AC-05 — immediate print uses persisted authority:** The immediate print lookup occurs only after a successful sale save and uses the returned `orderId`; token/CAE browser props do not themselves produce QR. A valid stored grant renders; no grant prints without QR.
- **AC-06 — resolver-to-render contract:** A non-empty server-resolved QR value reaches the QR generator in the visible/banner path and in the selected PDF/thermal path. Focused tests assert actual SVG markup or the expected QR image data URL, not merely that a resolver action was called.
- **AC-07 — reprint parity:** Standard historical/reprint PDF and thermal paths use the same server-resolved DTO policy as immediate print. Legacy version-0 raw behavior remains byte-preserving; version-1 without a valid grant remains `none`.
- **AC-08 — diagnostics/privacy:** Any added diagnostic is restricted to enumerated transition/result categories and contains no token, QR data, QR URL/Base64, CAE, CUIT, fiscal payload, or recipient personal data.
- **AC-09 — no invoice side effects:** QR failure or print resolution performs zero AFIP issue, query, reconciliation, or retry operations and does not alter the authorized invoice or its monetary/fiscal fields.
- **AC-10 — scope isolation:** Ordinary invoice resolution/printing does not read a partial-payment voucher or another order's QR record; existing partial-payment print behavior remains unchanged.
- **AC-11 — formatted issuer CUIT:** For a tenant Business CUIT containing visual separators (for example, `30-71234567-8`), QR issuance/validation uses the normalized 11 digits and builds the payload with numeric `cuit: 30712345678`; the standard path can create/consume the same-tenant grant and resolve/render its QR. The partial-payment print path independently builds its QR URL from that voucher's tenant Business and payloads the same numeric CUIT. Inputs whose normalized result is not exactly 11 digits produce no QR payload/grant or partial print URL. Normalization must not change `businessId`, stored Business data, AFIP credentials, or the outbound AFIP request/wire representation.
- **AC-12 — narrowly normalized consumer-final form:** Given `clientIvaCondition: "Consumidor Final"`, `clientDocumentType: ""`, and no `clientDocumentNumber`, `createAfipInvoiceDTO` accepts the form projection as document type absent; preparation builds `tipoDocRec: 99` and `nroDocRec: 0`, allowing the normal issue/grant path. For any other recipient condition or when a document number is supplied, empty document type remains invalid; no unrelated document-type validation is relaxed.
- **AC-13 — bounded server-only resolver diagnostics:** Grant creation, save consume/reference persistence, and resolver reason/selected kind use fixed server-side structured categories. Resolver `qrKind` is restricted to `verified-url`, `verified-raw`, `legacy-raw`, or `none`; resolver reasons are restricted to the documented allowlist. No identifiers, fiscal/personal data, QR/token/payload/URL values, arbitrary errors, or derived encodings are logged. Resolver diagnostics are absent from every browser-visible Action/DTO/prop/output, and QR failure never becomes a fiscal error or blocks CAE persistence.
- **AC-14 — diagnostic-to-render distinction:** Tests demonstrate that a resolver `none` event carries its allowlisted unavailability reason and the existing UI omits the QR while preserving invoice/CAE/print behavior. Separately, a non-`none` selected kind reports `QR-ready` internally and the existing visible UI renders SVG markup, while the current PDF/thermal path emits its expected image/PNG output. `QR-ready` alone is not accepted as renderer-success evidence; renderer outcome is independently reported under AC-16.
- **AC-15 — HTTP response semantics:** Tests/spec assertions do not infer QR readiness from HTTP 200 or Action completion/timing. An Action may successfully save an authorized CAE while grant creation, grant consumption/reference persistence, or QR resolution yields no QR; only the resolver's selected kind plus the downstream rendering result distinguish the ready/rendered path.
- **AC-16 — authenticated, privacy-safe renderer outcome report:** A dedicated Server Action authenticates every invocation and accepts only the exact two-field input `{ renderer, outcome }`, with `renderer ∈ {pdf, thermal-html, qz, partial}` and `outcome ∈ {generated, failed, submitted}`. Unknown enum values, wrong types, extra keys, and non-bounded input are rejected; invalid submissions are not logged with submitted data. For valid reports, server-only logs contain only those allowlisted enums and a fixed render stage/event; the browser receives no reason, `qrKind`, exception, or echoed input. Client reporting contains no QR content or order/tenant/CAE/URL/payload/token data. `generated` is emitted only after a non-empty QR SVG/PNG has been constructed; `submitted` only after successful handoff and explicitly does not guarantee physical printer output; `failed` does not carry a reason/message. The event is diagnostic and is not trusted as fiscal proof.
- **AC-17 — commit-accurate reference telemetry:** `reference-persisted` is emitted only after the enclosing Prisma transaction resolves successfully with the grant reference committed. A rollback/throw after the in-transaction write emits no `reference-persisted`. If the event must remain in the callback, it is renamed `reference-staged`, and tests/spec/reporting do not treat it as a committed reference.
- **AC-18 — outcome evidence is distinct from resolver state and physical printing:** `qrKind` and resolver `reason` remain internal and are never client supplied or returned through the renderer report action. A reported `generated` indicates only constructed non-empty QR SVG/PNG; `submitted` indicates successful software handoff only. Neither event proves successful physical printer output, and no QR content is necessary or permitted in the report.
- **AC-19 — never burn an unparseable token:** Every grant claim, including Decimal amount, is normalized and validated before the one-use CAS. For any invalid/unparseable claim, `consumedAt` remains unchanged and no consumed grant is returned; a valid later attempt can consume it. Valid money bindings compare exactly in Decimal space, without float conversion or tolerance.
- **AC-20 — atomic normal order association:** For a valid consumed grant, order creation, `orderId` CAS/link, and `CAE.qrAttestationId` persistence commit or roll back together. Successful commit yields matching relation and JSON reference; a failed order transaction leaves no committed consumption/link/reference. `orderId` is nullable/unique/FK-backed and grants are linked only after `Order` creation.
- **AC-21 — one-time safe recovery:** An authenticated tenant-scoped repair links an already-consumed grant with null `orderId` only if exactly one candidate matches every required order/Business binding, including exact Decimal amount and normalized issuer CUIT/recipient. It must win CAS `null -> order.id` and atomically persist the CAE JSON reference. Zero/multiple candidates, any mismatch/missing binding, or CAS loss leaves the order unrepaired and print resolution at `none`; no grant can be reassigned. Repair does not call AFIP/ARCA or alter/reissue CAE.
- **AC-22 — additive migration and rollout:** The already-applied prior migration is not edited. A new migration adds nullable unique `AuthorizedArcaQrGrant.orderId` and its `Order` FK relation without guessing links for existing rows. This task does not apply the migration; implementation release requires deploying it and regenerating/deploying Prisma Client compatibly.

## Remaining verification boundaries

- The runtime events and migration-applied status are user-provided evidence; this specification session did not query the production database, independently capture logs, or verify the live Prisma migration table. Implementation/QA must verify the fix in an isolated PostgreSQL integration environment and perform the normal deploy migration rollout.
- The production root cause is nevertheless assigned from the supplied event sequence plus the described code/schema behavior: grant creation succeeds, Prisma Decimal parsing fails after consumption CAS, the order is saved without reference, and policy-v1 correctly returns no QR. Renderer work is not indicated unless a post-fix resolver returns a non-empty QR and image generation still fails.
- No live AFIP/ARCA certification claim is implied by these acceptance criteria. Never repeat external CAE issuance to test recovery.
