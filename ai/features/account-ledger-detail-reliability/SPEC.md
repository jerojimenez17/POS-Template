## Findings from the inspected implementation and evidence

1. The current `page.tsx` awaits `params` and `searchParams` together, then awaits `auth()`. If the session has no business ID, it redirects. After that it starts two independent reads together with `Promise.all`: a tenant-scoped `order.findUnique` (`where: { id, businessId: session.user.businessId }`) and `business.findUnique` for that same session business's `ptoVenta`. The order select includes client, items, every cash movement ordered newest first, and nested payment-voucher `status` plus at most the latest failed attempt's `billType` (filtered/order/take projection). Measure these waits independently; do not infer that the nested projection is a particular slow SQL/query plan.
2. `loading.tsx` and `error.tsx` now exist at the route segment. The loading fallback is an accessible skeleton; the error boundary returns safe generic text and retry. These are useful only after Next can compile/serve the segment boundary. They do not explain the current absence of an observed detail navigation request.
3. Direct page imports include `auth`, Next navigation/link, Prisma types, the DB singleton, UI primitives, Lucide icons, and local `AddPaymentForm`, `CancelOrderButton`, `EditableOrderDetailWrapper`, and `PrintOrderButton`, plus `LocalDate`, `PaymentVoucherRowActionClient`, and the type-only `ClientFiscalData` import. The local/client components in turn reference actions, shared account-ledger controls, printing utilities, and the editable ledger component. This is a plausible nontrivial Turbopack module graph, but source inspection alone does not show which module (if any) stalls compilation.
4. The root layout also participates in route requests and imports Google fonts, global styles, navigation, auth/session and context providers, payment-status guard, Web Vitals, and Toaster. A route-only investigation must compare against a control route in the same server, because a shared/root graph or environment issue could otherwise be misattributed to this page.
5. `package.json` declares `next: ^16.2.7`; the lockfile resolves `node_modules/next` to 16.2.7. `npm run dev` is `next dev --turbopack`; `npm run build` is `next build`. `next.config.ts` has no `turbopack` configuration: it sets a 10 MB Server Actions body limit and image settings only. Thus the observed dev path is Turbopack, whereas production build/typegen passing are not a reproduction of the same dev compilation path.
6. The installed `node_modules/next/dist/docs/` and package files were not available to inspect in this workspace snapshot (the `node_modules` tree is absent). No version-specific Turbopack behavior or alternate dev command is asserted. This is secondary unless new correlated evidence points back to compilation.
7. The latest 227 ms filesystem benchmark is a possible environment factor, not proof of a compiler/cache blocker. The earlier disk/cache warning is likewise only a possible confounder. Do not clear `.next` or claim cache causality without request-correlated evidence.
8. The live evidence confirms the detail compile line reappears on a click and the detail Document remains pending beyond 120 seconds, while the list is already slow (9.4 s application time) and auth-session requests complete in 324–561 ms during the pending detail Document. Neither fact localizes the slow list to this defect or proves detail auth is fast: the route request and the session endpoint are different work. The missing page-function marker is consistent with compilation/module loading before invocation, but cannot exclude a server-side wait after request dispatch. This is a confirmed development-route reliability regression; do not describe the code as unaffected or the symptom as a mere diagnostic uncertainty.
9. Initial route rendering does not issue a payment voucher. Existing child action feedback findings remain independent of this suspected dev compilation stall.
10. **Current click/request-source inspection:** `AccountLedgerList.tsx` renders explicit `next/link` targets inside `Button asChild` (Radix Slot): “Ver” and Print use `/account-ledger/${order.id}`, Pay uses that exact path with `?action=payment`, and Cancel uses it with `?action=cancel`. This source inspection makes the anchor targets concrete but does not prove which element was clicked at runtime, whether the click was intercepted elsewhere, whether a prefetched/cached transition was served, or whether the request went to the log source's origin/port. The logged POST is not enough to identify its action/payload safely; do not infer it is the detail page request.

## Architecture decisions

- Keep the detail page server-rendered and preserve session-derived tenant scoping. Never move privileged data access into an unauthenticated client fetch.
- Diagnose the currently pending detail Document at the route boundary and compilation boundary first; capture document and server process identity/timestamps. The detail click can trigger a document navigation as well as RSC traffic, so record both rather than presuming a client transition. For list navigation also inspect App Router/RSC traffic and prefetch/cache use. If a request exists in DevTools but not in terminal logs, reconcile destination origin/port, proxy/log source, and timestamp before concluding it did not reach Next. Compare current branch changes—including untracked route dependencies—to `HEAD`/main before attributing the regression to unrelated page data reads.
- Preserve the existing route-segment loading and error UI: the skeleton improves navigation after compilation and the client error boundary handles server render failures. Follow the installed Next.js error-boundary contract (`'use client'`, safe generic text, retry). Do not render `error.message`, Prisma/SQL details, credentials, AFIP data, or raw payloads to users. A digest may be used only as a non-sensitive support correlation value if appropriate. Neither boundary is a remedy for a compiler that has not produced a response.
- After auth succeeds, run independent reads concurrently where practical. Use explicit Prisma `select` projections consistent with the page and its client children. Do not introduce per-row queries or change the all-history semantics without a separately approved pagination requirement.
- Preserve the not-found presentation for a missing or out-of-tenant order. Keep authorization before rendering any order details.
- Make action failures observable at their interaction point: visible, safe feedback and a recoverable retry where retry is safe. Never offer a retry for payment-voucher `UNKNOWN` or in-progress states; do not collapse payment success and voucher outcome into a single ambiguous result.
- No schema or migration change is expected for this route UX/performance issue. No new dependency is expected.

### Route loading and latency

- **AC1 — Immediate loading state:** navigating directly to or client-navigating to a detail URL displays a route-appropriate skeleton while the detail data is unresolved. The fallback contains no order/customer data and is keyboard/screen-reader understandable.
- **AC2 — Stream/first-visible-content:** in staging with warm application/database connections, a 20-navigation sample against a representative order (up to 100 items and 100 payment movements) has p95 time-to-visible-loading-fallback of **<= 500 ms**. The measurement must state client/network conditions and exclude the one-time development compile unless separately measured.
- **AC3 — Detail completion:** under that same fixed staging setup, p95 navigation-to-interactive-detail is **<= 1.5 seconds**, or improves by **at least 40%** over a captured pre-change baseline if the existing baseline is already above the target. Record database-read and render timings separately; do not claim a latency improvement without measurements.
- **AC4 — No avoidable sequential read:** once session/business authorization is resolved, independent order-detail and business POS reads do not wait on each other. The resulting page preserves the current not-found and tenant-scoped behavior.
- **AC5 — Query/payload scope:** returned Prisma fields are limited to values consumed by the detail page and its children. All currently visible order items/payment rows and the voucher state/proposal data remain correct. No N+1 query is introduced; the query count per request is independent of the number of items/movements (excluding separately invoked client actions).
- **AC6 — Voucher boundary:** initial route rendering makes zero AFIP/ARCA issue/sequence requests. Adding the skeleton, error boundary, projection, or query parallelism does not alter voucher attempts or their persisted state.

### Errors and recovery

- **AC7 — Server render failure:** an injected/controlled order-query or business-query failure displays a localized generic failure message and a working retry control. The response does not expose SQL, Prisma error text, stack traces, credentials, raw AFIP details, customer fiscal identifiers, or unrestricted database records.
- **AC8 — Missing/unauthorized record:** an absent order and an order outside the authenticated business continue to show the existing safe not-found experience (or equivalent non-enumerating behavior); no details are streamed before authorization.
- **AC9 — Payment action feedback:** a failed payment registration visibly reports that the payment was not registered; if payment persistence succeeded but voucher issuance failed/was indeterminate, the UI explicitly reports payment recorded and distinguishes definite failure from verification-required `UNKNOWN`. Safe failures are not silently swallowed.
- **AC10 — Voucher-row action feedback:** errors from status retrieval and payment-voucher print are surfaced as safe, accessible inline/toast feedback. A failure does not fabricate `AUTHORIZED`; `UNKNOWN` remains non-retryable and printing does not issue another voucher.
- **AC11 — Privacy:** user-visible errors contain only allowlisted generic text/status and, optionally, an opaque diagnostic correlation identifier. Server logs contain no credentials, tokens, certificates, full customer identifiers, CAE, raw upstream payload, or raw error object.
