# AFIP invoice voucher or explicit no-AFIP choice for each account-ledger payment

## Status and scope

- **Status:** Architecture and acceptance specification, updated for the reported Remito failure and incorrect printed voucher number. The remediation is specification-only; no implementation or tests are included in this update.
- **Branch:** `feature/afip-partial-payment-voucher` (reported as created by the user).
- **Goal:** for each individual account-ledger payment, preserve the existing A/B/C behavior of attempting a separate AFIP/ARCA Factura for that payment as a partial payment, or allow the operator to explicitly select **Remito (sin emisión AFIP)**. Associate any issued invoice—or the durable intentional no-voucher decision—only with that payment.
- **User decisions preserved:** Factura A/B/C retain the one generic line described as **“Pago parcial”**, operator-selected invoice type and configured POS; positive ARS payment inputs normalize to whole pesos using standard `Math.round` (halves up), and an authorized invoice total must exactly equal the saved payment movement. Selecting Remito instead records the payment without an AFIP invoice, and that payment's history must not offer invoice creation/retry. Factura A/B/C behavior remains unchanged.
- **Out of scope:** changing the existing order invoice, replacing `Order.CAE` or its fiscal metadata, issuing a voucher for the full order, modifying invoice/credit-note eligibility rules, deciding a new IVA/tax treatment, automatic duplicate recovery after an ambiguous remote outcome, or changing unrelated ledger/payment behavior. Editing the linked `Client`'s saved fiscal/customer data is explicitly in scope as one persistent, account-level Client update; it must not edit the historical `Order` fiscal snapshot. Customer fiscal details are not edited from individual payment/voucher rows.

## Existing behavior and constraints observed

- `prisma/schema.prisma` stores account-ledger payments as `CashMovement` rows. Each row has its own `id`, `orderId`, `businessId`, `total` (`Float`), `date` and `paidMethod`; it currently has no invoice association. An order separately stores its original invoice in `Order.CAE`, `billType`, `afipVoucherType`, `invoiceNumber`, `invoicePointOfSale`, `invoiceIssuedAt` and `fiscalSnapshot`.
- `registerPayment` in `src/actions/unpaid-orders.ts` creates one `CashMovement` inside a Prisma transaction, updates existing client/order accounting, then emits cache/Pusher updates and invokes payment-voucher issuance. It currently accepts fractional amounts and its whole-unit balance behavior is not a consistent normalization contract. Normalize positive ARS input to whole pesos before persistence, reject a normalized payment below 1 peso before the transaction or any AFIP call, and perform all balance calculations using integer whole pesos. For A/B/C, a Pusher error after commit must not short-circuit cache-tag revalidation or the automatic voucher attempt; for Remito, cache/Pusher handling remains but there is no voucher attempt.
- The account-ledger detail page at `src/app/(protected)/account-ledger/[id]/page.tsx` queries an order scoped to the session business and renders each `cashMovement` in “Historial de Pagos”; this is the current individual payment-row UI. `AccountLedgerList.tsx` lists orders, not their individual movements.
- The AFIP path is already server-side: `src/actions/afip.ts` authenticates and calls `prepareAfipVoucherForActor` then `issuePreparedAfipVoucher` from `src/lib/server/afip-voucher.ts`. Preparation validates a positive invoice total, supported invoice type, POS and credentials, and does a read-only sequence lookup; issuance then POSTs `action: "createVoucher"` to the remote AFIP function. The HTTP call cannot participate in a Prisma transaction. The function currently receives products with `id`, `code`, `description`, `price`, `salePrice`, `amount`, a bill type, client fields and total; it has no payment-voucher-specific idempotency contract documented in this repository.
- Existing supported AFIP invoice types are A/B/C, mapped to WSFE types 1/6/11. `Remito` and `Presupuesto` are UI document kinds, not invoice types accepted by `normalizeAfipInvoiceDTO` for CAE issuance.
- Normal sale checkout has separate Factura and Remito controls in `BillButtons`. Factura invokes the AFIP action before persisting the sale; Remito takes the `createSale(false, false)` path, saves the sale with `billType: "Remito"` and without an AFIP-issued CAE, then prints the sale snapshot through the existing sale-print path. `processSaleAction` only accepts/consumes trusted fiscal issuance data for A/B/C. This behavior is for a full sale/order, not an account-ledger payment.
- Current source now presents A/B/C and Remito; `AddPaymentForm` omits POS for Remito. `registerPayment` validates the choice, inserts one `CashMovement`, writes a `PaymentVoucher(NOT_REQUIRED)` in that same transaction for Remito, and updates existing client/order accounting once. After commit it returns without calling voucher issuance for Remito; A/B/C still go through the separate post-commit issuance path. History renders `NOT_REQUIRED` passively. These source paths do not by themselves prove the deployed generated Prisma client or database has the model/status/migration.
- The existing normal-sale Remito print path prints an order/product sale snapshot, not a receipt for a later partial account payment. Do not reuse that print path or imply that a payment-level Remito document is printed or AFIP-issued. In this feature, Remito is the operator's label for the payment's explicit no-AFIP selection. If a legally compliant dispatch/transport Remito is intended, that is a separate requirement and is not fulfilled by this choice. This specification makes no claim about the legal status or permissibility of a transaction; “venta en negro” is not product copy or a legal classification.
- Existing server actions are public endpoints. The installed Next.js documentation (`node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md` and `.../02-guides/{authentication,data-security}.md`) requires validation, authentication and resource authorization inside each action and minimal DTO return values. The installed Next.js is `^16.2.7` (not the version in top-level `AGENTS.md`); follow installed docs plus existing repo patterns.
- Prisma uses PostgreSQL. The payment-voucher base migration provides the payment-level fiscal association, but the published/applied `20261104000000_add_payment_vouchers` migration predates the later addition of `NOT_REQUIRED`. That already-published migration is immutable: restore it to its committed content and add a new additive migration for the enum value. Do not rely on editing/replaying the base migration to upgrade existing databases.
- Persistent customer editing already follows `src/components/clients/ClientsPageClient.tsx` + `ClientForm.tsx` and the tenant-scoped `updateClient` Server Action in `src/actions/clients.ts`; `updateClientSchema` is strict and must be extended for any new fiscal identity fields. The current `Client` model contains `cuit` and `ivaCondition`, but no document-type/document-number pair. The `Order` model separately has `clientIvaCondition`, `clientDocumentType` and `clientDocumentNumber`; these are historical order fields and must remain unchanged by payment-voucher work.
- The existing invoice parameter UI (`src/app/(protected)/newBill/page.tsx`, `BillProvider`, `BillParametersForm`) receives the authenticated business `ptoVenta` list, defaults to its first configured POS, allows choosing a configured POS and A/B/C type, and carries identity as `clientDocumentType` (`CUIT` or `DNI`) plus text `documentNumber`. Its form currently renders identity controls only when IVA condition is not Consumidor Final. This demonstrates app data shape/behavior only; it does not prove AFIP legal acceptance of either identifier for every Factura A case.
- Existing invoice printing in `PrintableTable.tsx` uses `clientIvaCondition`, `clientDocumentNumber` and `clientDocumentType`/`typeDocument`; it prints the recipient document when the invoice flow's IVA condition is non-Consumer Final. Payment-voucher printing must instead use its immutable attempt snapshot, including the document type/number, and must not read the current `Client` or order invoice at reprint time.
- `/newBill` passes `ptoVentas[0]` to `BillProvider` as default; `BillParametersForm` lets the operator select a configured point and bill type and synchronizes the chosen POS into bill state. Mirror this configured-POS pattern only for account-ledger A/B/C payment and retry flows; the Remito/no-AFIP choice needs no POS. Every proposed A/B/C POS remains untrusted until the server checks membership in the authenticated business's current `Business.ptoVenta`.

## Functional requirements and architecture

### R1 — One voucher association per individual payment

1. Treat the `CashMovement` row as the payment identity. Each eligible individual movement can have at most one successful payment invoice; multiple distinct movements on the same order each get a distinct invoice, even when their amounts are equal.
2. Add a payment-voucher record with a unique foreign key to `CashMovement` (one-to-one association). Do not write any payment voucher fields into `Order.CAE`, `Order.billType`, `Order.invoiceNumber`, `Order.invoicePointOfSale`, `Order.invoiceIssuedAt` or `Order.fiscalSnapshot`.
3. Preserve a successful voucher's type, AFIP type code, POS, invoice number, CAE, issue timestamp, exact total and minimal trusted fiscal/print snapshot on the payment-voucher record, not on the order. Preserve the issuing payment's type and amount once issuance starts; a retry must not mutate an already successful voucher.
4. Retain all existing `Order` invoice data byte-for-byte/semantically unchanged during payment voucher creation, failure, retry and print.
5. A payment recorded with Remito has an explicit durable `NOT_REQUIRED` payment-voucher state, not a missing voucher or issuance failure. Set `billType = "Remito"`, the normalized payment amount and null AFIP-only fields, with no attempt rows. Create this association in the same transaction as its `CashMovement`, so a committed Remito payment can never transiently appear `MISSING` and offer invoice creation.

### R2 — Recommended persistence contract

Use the existing `CashMovement` as the source payment and a dedicated `PaymentVoucher` (or equivalently named) Prisma model rather than extending `Order`. For an A/B/C issuance it stores the invoice lifecycle described below. For a Remito selection it stores the payment's explicit no-voucher decision as `NOT_REQUIRED`, with no AFIP attempt or invoice data:

```text
PaymentVoucher
  id                 String primary key
  cashMovementId     String unique FK -> CashMovement.id
  businessId         String FK -> Business.id (same tenant as movement/order)
  status             NOT_REQUIRED | PENDING | ISSUING | AUTHORIZED | FAILED | UNKNOWN
  amount             Decimal @db.Decimal(12, 2) (immutable snapshot; whole pesos, fractional part zero)
  billType           Remito | Factura A | Factura B | Factura C (selected by operator)
  afipVoucherType    Int? (null for NOT_REQUIRED; otherwise 1 | 6 | 11 from billType)
  invoiceNumber      Int?
  invoicePointOfSale Int?
  cae                String?
  issuedAt           DateTime?
  fiscalSnapshot     Json? (trusted server-derived minimal snapshot only)
  currentAttempt     Int
  lastErrorCode      String? (allowlisted/sanitized; never raw provider payload)
  createdAt/updatedAt DateTime

PaymentVoucherAttempt (recommended audit/retry record)
  id                 String primary key / opaque idempotency token
  paymentVoucherId   String FK -> PaymentVoucher.id
  attemptNumber      Int; unique(paymentVoucherId, attemptNumber)
  status             PREPARING | ISSUING | AUTHORIZED | FAILED | UNKNOWN (no attempt row for NOT_REQUIRED)
  billType           Factura A | Factura B | Factura C
   amount             Decimal @db.Decimal(12, 2) (whole pesos, fractional part zero)
  invoicePointOfSale Int (selected, server-validated POS for this attempt)
  recipientSnapshot  Json (immutable, minimal server-derived recipient name,
                           effective IVA condition, document type/number)
  startedAt/finishedAt DateTime
  safeErrorCode      String?
  observedAuthorizedTotal String? (bounded exact decimal text from trusted response; never rounded)
```

The model names/column casing may follow local Prisma conventions. Add indexes for `businessId`, `cashMovementId` and attempt lookup; use foreign keys/cascade policy consistent with the application's accounting-retention rules (do not cascade-delete fiscal records just because a ledger UI row is removed). `PaymentVoucher.cashMovementId` uniqueness is the database-level defense against multiple successful voucher associations for one payment. Each retry is a distinct attempt record, but there remains one current voucher association. For Remito, transactionally create the association with status `NOT_REQUIRED`, `billType = Remito`, saved normalized amount, no attempts and null AFIP-only fields. This status is deliberately not `MISSING`, `FAILED`, or `AUTHORIZED`; it is terminal for payment-level invoice actions and must never enter the AFIP orchestration/reconciliation or printing paths.

Store user-input/order/payment monetary snapshots in the existing Decimal representation if appropriate, but their authoritative value is an integer number of pesos (fractional part zero); convert at boundaries without binary-float arithmetic. For every positive ARS input or legacy order/payment amount, normalize to nearest whole peso using standard JavaScript `Math.round` semantics (for positive values, exact halves round up). Normalize each source order total, each prior movement, and the submitted payment before balance arithmetic; then calculate order/prior/payment/remaining amounts and paid status using integer whole pesos only. A submitted payment must be finite and its normalized result must be at least 1 peso before persistence or AFIP work. Also reject a normalized amount above **9,999,999,999 pesos**, the largest whole-peso value representable by `PaymentVoucher.amount Decimal(12,2)`, before the payment transaction can commit; this prevents a committed payment whose voucher reservation cannot store its amount. This intentionally means `0.1 + 0.2` normalizes to 0 and is rejected, while `10.5` normalizes to 11. Reject invalid non-finite, negative, or unsafe-range source values rather than substituting a value. **Do not normalize a returned or reconciled AFIP authorized total:** compare trusted evidence as an exact numeric decimal value against the immutable whole-peso movement amount, without rounding or tolerance. Numeric/textual forms `123`, `123.0`, and `123.00` equal 123 pesos; `123.4` is non-whole and mismatched even if rounding yields 123. Persist a bounded exact decimal-text representation of an observed total when needed for safe reconciliation evidence; never replace it with a rounded value or persist raw provider payloads. This feature does not authorize an unreviewed wholesale monetary schema migration. Every individual attempt must also freeze the bill type, validated selected POS and the precise recipient snapshot used to build the external request. Attempts for every payment on the account re-fetch the same linked, persistent Client; each new attempt snapshots that Client's then-current effective saved fiscal identity (typed pair when present, otherwise legacy `cuit` as CUIT), other saved data, and any type-specific recipient projection. A later Client edit affects only subsequent attempts, never an earlier attempt or an authorized voucher's print snapshot.

### Customer fiscal identity extension

The Client edit control is a persistent, account-level Client edit, not a voucher-local or payment-row form. In account-ledger detail, make the linked Client's fiscal identity/Client field clickable and editable; it opens one accessible account-level modal populated from that Client. When opening the modal, use the typed identity pair if complete; if both typed fields are absent and legacy `Client.cuit` is non-empty, populate the form as `CUIT` with that legacy value. Do not provide a customer-data edit button, dialog, or editor inside each payment/voucher row. Reuse the existing `ClientForm` and `updateClient` conventions. Extend the Client persistence/action DTO and strict Zod update schema to support the same recipient identity pair used by `newBill`: document type `CUIT | DNI` and document number as a string (preserve leading zeroes). The pair is either both absent or both present; never accept simultaneous CUIT and DNI values. Keep the existing `Client.cuit` field and its current search/list compatibility. On every save, atomically synchronize the fields in the same tenant-scoped Client update: CUIT saves `fiscalDocumentType = CUIT`, `fiscalDocumentNumber = number`, and `cuit = number`; DNI saves the typed DNI pair and clears `cuit`; explicit clearing saves both typed fields as null and clears `cuit`. Thus, a non-empty legacy `cuit` is an effective CUIT only when no typed pair exists, and typed identity is authoritative otherwise. Any migration/backfill must preserve `cuit` and must not invent DNI data. Validation of identifier *format* must follow the established app input contract, not be represented as proof of AFIP authorization.

The update action must authenticate and scope the Client by `session.user.businessId` on every call, as current `updateClient` does; the caller supplies only `clientId` and editable Client fields. A successful save atomically persists `ivaCondition`, both typed identity fields, and the synchronized legacy `cuit`, then refreshes the existing clients caches. The update must not alter the order's client relation or any `Order` invoice/fiscal field. Every payment's create/retry action re-fetches that account's linked Client and resolves its current effective identity (typed pair first; otherwise non-empty legacy `cuit` as CUIT); no customer values from a payment row or voucher action are authoritative. For a Factura A recipient, the account-level modal may save exactly one of CUIT or DNI and its matching single number; expose these identity controls even when the saved Client IVA condition is Consumidor Final (do not copy `newBill`'s IVA-based visibility condition as a gate). When the document type changes in the modal, clear the old document number immediately. The operator must enter a number for the newly selected type before saving that type; alternatively, clearing the identity must atomically save both typed fields and legacy `cuit` as absent. The Zod schema must enforce both-or-neither. The server action must compare the requested pair with the persisted effective pair (including a legacy CUIT prefill): if the type changes, reject a request that reuses the old number, even if both fields are submitted, as well as any type-only/half update. This is an app payload contract, not a statement that either identifier is legally accepted by AFIP in all Factura A cases; retain the existing gateway/owner validation blocker below.

### R3 — Payment creation and voucher issuance flow

1. Before registering a payment, the operator selects Factura A/B/C or Remito. For A/B/C, require a POS from the authenticated business's configured `Business.ptoVenta`, show the normalized whole-peso amount, selected type and POS before submission, and default POS to the first configured value. The form and server use the same whole-peso policy, with the server independently validating it before persistence. After commit, A/B/C automatically attempts invoice issuance and leaves the payment row actionable if issuance fails. For Remito, identify the choice as **“Remito (sin emisión AFIP)”**, show the normalized amount and that no AFIP invoice will be requested, and do not require/display a POS for issuance. The Remito branch records the payment plus `NOT_REQUIRED` metadata and does not start an automatic AFIP attempt. In either branch, payment success is distinct from any A/B/C invoice outcome.
2. The A/B/C create/retry boundary takes only `cashMovementId`, supported A/B/C `billType` proposal and selected `ptoVenta` proposal, plus explicit retry intent where applicable. It must reject Remito, Presupuesto, credit notes and unsupported values at this AFIP boundary, and ignore/deny caller-supplied `businessId`, actor, amount, client identity/IVA data, order total, CAE, invoice number, products, fiscal snapshot or credentials. Re-fetch the payment, its order, linked Client and Business on the server and derive all authorization/tenant context from `auth()`. Validate the proposed POS as a safe positive integer that is a member of the authenticated business's current `Business.ptoVenta`; persist the validated POS in that attempt before the external call. The one-time Remito selection is an initial payment-registration choice, not a retry/create-voucher action.
3. Build a fresh, explicit server-side AFIP invoice DTO from the selected payment's trusted context. It contains exactly one line with description `Pago parcial`, quantity `1`, no discount, and line amount equal to the stored payment amount. Set the request invoice total and total-without-discount to that same amount, with zero discount. Do not include order items and do not derive the voucher total from `Order.total`, paid-to-date, or remaining balance.
4. Build the recipient snapshot from the linked persistent Client re-fetched by server, including name, saved IVA condition and exactly one optional effective identity pair (typed pair first, otherwise a non-empty legacy `cuit` as CUIT). The single account-level editor updates this Client persistently through the tenant-scoped Client edit action; it does not edit the order or an individual payment/voucher. Every payment attempt for this account reads this same linked Client's current persisted data. If the selected type is Factura B, force the recipient IVA condition sent to the gateway and stored on that attempt/voucher's fiscal snapshot to exactly `Consumidor Final`, regardless of the Client's saved IVA condition. This is a per-voucher projection only: do not update the Client to Consumidor Final. For Factura A, permit the single persisted CUIT or DNI identity pair in the app DTO; do not claim either is fiscally accepted for every case absent the gateway/owner's established validation. Reuse the existing AFIP preparation/issuance safeguards and the selected server-validated POS. The operator selects invoice type; the server validates it against A/B/C and maps to 1/6/11. Do not silently infer/replace the operator's type. An existing AFIP or customer-data rejection is a pre-issue/definite failure only when it is known no remote request could have authorized a voucher, not permission to issue another type automatically.
5. Do not call AFIP while holding an open database transaction. For A/B/C, short transaction 1 validates tenant/resource/payment and the currently configured POS, resolves the server-side recipient projection (including Factura B's forced IVA condition), atomically creates or claims the unique voucher row and a new attempt, and stores immutable amount/type/POS/recipient snapshot in a `PREPARING` phase. Then outside the transaction perform read-only ARCA sequence lookup and deterministic invoice validation, mapping, DTO construction, serialization, and request preparation. Only when `issuePreparedAfipVoucher` is ready to invoke the actual HTTP transport (`axios.post`) may it invoke the durable dispatch-marker callback immediately before transport. If marker persistence fails, do not call transport. A short second transaction persists the verified outcome and attempt state. Use conditional transitions/unique constraints so replay/concurrency cannot produce duplicate issuance. Remito bypasses this whole AFIP path: within the existing serialized payment transaction, write exactly one `CashMovement`, update existing order/client accounting once, and create its `NOT_REQUIRED` association atomically; make no AFIP preparation, sequence, credential, dispatch-marker, transport, or reconciliation call.
6. Classify issuance errors by the actual transport phase, not by a broad error category or an orchestration flag set before entering the AFIP adapter. Validation, reservation, configuration/credential checks, sequence lookup, DTO construction, request serialization/preparation, and any other failure before the durable dispatch-marker callback are definite `FAILED` outcomes, must be surfaced as visible safe failure feedback, and can be explicitly retried after revalidation. The durable marker/callback belongs at the final adapter boundary immediately before the actual HTTP transport call; setting `remoteDispatchPossible` before calling the adapter is not sufficient evidence of possible dispatch. Once the marker is durably recorded, an exception may be `UNKNOWN` because dispatch may have occurred, unless an upstream response unambiguously confirms that no voucher was authorized. `UNKNOWN` is otherwise reserved for failures after the request may have been dispatched (including timeout, connection reset, malformed/indeterminate response after dispatch, or process/persistence failure after possible dispatch). A definitive ARCA rejection after dispatch may be `FAILED` and retryable only when the upstream response unambiguously confirms that no voucher was authorized. Success must be validated and durably attached to that payment before returning printable status.
7. If the process crashes while the attempt is still durably in known pre-dispatch `PREPARING`, or any validation/preparation/reservation/marker-persistence error occurs before the transport callback completes, record/resolve it as definite `FAILED` and make no HTTP request. If it crashes after the durable potentially-dispatched `ISSUING` transition, or a timeout/connection reset/malformed response occurs after the request may have reached AFIP, mark or retain `UNKNOWN`, not `FAILED`. Never automatically retry, delete the reservation, or permit a second issuance in `UNKNOWN`. A stale `ISSUING` attempt is treated as `UNKNOWN` until reconciled. The current repository does not prove that the remote create API accepts an idempotency token, so a local idempotency key protects the app's concurrency but cannot make an already-dispatched remote request exactly-once.
8. `UNKNOWN` requires a safe authoritative reconciliation path before any retry or attachment. Until the specific payment's outcome is established, display a “verificar emisión” state and block create/retry. If reconciliation confirms an authorized voucher, compare its trusted returned total exactly (no rounding/tolerance) with the immutable whole-peso payment amount before attaching/authorizing it. A non-whole or mismatched total remains persisted as `UNKNOWN`, with reconciliation-required metadata, non-printable and blocked from replacement issuance. Only after an exact match may the confirmed voucher be attached and become `AUTHORIZED`. If reconciliation confirms absence/rejection, allow a new attempt. Do not invent a `getVoucher` operation or treat `getLastVoucher` alone as proof that a specific voucher belongs to this payment.
9. If the external call succeeds but persisting its response fails, retain/recover the attempt as `UNKNOWN` and surface it for reconciliation; never report ordinary “failed; click retry” or issue another invoice automatically.
10. If AFIP returns success but the trusted returned total is non-whole or differs from the immutable whole-peso payment snapshot, compare exactly without rounding, persist the observed total using the existing safe observed-evidence fields plus only validated/allowlisted voucher evidence (for example, recognized CAE and invoice identifiers) sufficient for reconciliation and duplicate prevention, and keep the voucher/attempt status `UNKNOWN`. Set reconciliation-required metadata using the existing safe metadata/error-code mechanism (for example, the existing `lastErrorCode` and `safeErrorCode` fields); do not add a status enum value or schema field for this condition. Do not classify it as `AUTHORIZED`, expose it as printable, claim the amount requirement passed, or permit replacement issuance. Preserve payment/order amounts and do not retain raw AFIP payload/response. Exact-equivalent forms such as `123.00` match an expected 123; `123.4` does not.
11. `registerPayment` must validate the submitted amount as finite, normalize it to the nearest whole peso using standard `Math.round` semantics (positive halves up), and verify the normalized result is within **1..9,999,999,999 pesos** before opening its payment database transaction and before any AFIP preparation/issuance. The upper bound is required by `PaymentVoucher.amount Decimal(12,2)` and must be rejected before committing the `CashMovement`, not later when reserving its voucher. For example, `0.1 + 0.2` normalizes to 0 and is rejected, `10.5` normalizes to 11, and a normalized value of 10,000,000,000 is rejected without committing a payment. Persist the normalized amount. Normalize the order total and each prior movement by the same policy, then perform overpayment checks, remaining-balance derivation and paid-status decisions using integer whole pesos only. Convert to/from the persisted numeric representation only at explicit boundaries.
12. After payment commit, treat Pusher emission and cache-tag revalidation as independent side effects. For A/B/C, also treat automatic voucher issuance as an independent post-commit side effect: one failure must not suppress the others. Remito has no voucher side effect because its `NOT_REQUIRED` association was already written atomically with the payment. Handle/report any side-effect failures separately from payment outcome; never claim rollback when the `CashMovement` transaction committed.
13. Serialize payment registration per order inside the database transaction before reading its current payment total and deciding whether the proposed amount fits. Use a PostgreSQL row lock on the parent Order (or an equivalent serializable transaction with correctly handled serialization retries); the balance read, overpayment decision, movement insert, client balance change, and paid-status update must participate in the same serialized transaction. A lock/transaction failure must not be treated as a committed payment. Do not rely on a client-side balance check or process-local mutex.
14. Account-ledger detail must normalize the order total and each payment movement to whole pesos with the policy in R2, derive `totalPaid` and `remainingBalance` as integers, and render all monetary values without fractional digits. Pass the same normalized whole-peso remaining balance to `AddPaymentForm` as its initial amount, maximum, and validation reference. Do not show or submit fractional digits.
15. The public `registerPayment` action may return only explicitly allowlisted, user-safe business messages for expected validation/domain outcomes (including invalid payment data, unauthorized/not-found order, invalid balance, and overpayment). Never return arbitrary `Error.message`, database/provider text, stack data, or thrown values. Map known domain failures to the allowlist; every unexpected exception returns one generic safe message (for example, `No se pudo registrar el pago. Intente nuevamente.`) while diagnostic logging remains server-only and sanitized. Preserve the committed-payment distinction for post-commit voucher/side-effect outcomes.
16. Remove the unapproved diagnostic-only account-ledger timing instrumentation: delete `src/lib/server/account-ledger-detail-timing.ts` and its diagnostic-only test `src/__tests__/account-ledger-detail-timing.test.ts`, and remove its import and `account-ledger-detail-timing` logging from the ledger detail page. Retain useful account-ledger loading, empty, and error UI and its non-diagnostic reliability behavior/tests. Do not modify `/searchBill` or its behavior as part of this cleanup.

### R4 — Authorization and tenant isolation

- Every mutation/read action authenticates independently and validates its input with the project's Zod/action pattern.
- Require an authenticated user with a business id; derive that business from the session. Preserve the existing account-ledger actor policy unless role/feature gates already apply to payment operations; do not create an AFIP entitlement or write-block bypass. For Factura A/B/C issuing/retrying, enforce persisted `hasAfipBilling === true`, AFIP credential/configuration and existing `requireFeature`/account-status checks at preparation and immediately before the irreversible POST, as in current AFIP issuance. A Remito payment still requires normal payment and tenant authorization but does not require AFIP credentials, AFIP entitlement or a configured POS because it performs no AFIP work; it cannot bypass checks on ordinary AFIP operations.
- Re-fetch `CashMovement` by `id + businessId` and verify its parent `Order.businessId` is the same tenant. Never accept an arbitrary client-selected movement/order/business relation. A missing/cross-tenant movement returns the same safe not-found/authorization behavior and causes zero ARCA calls.
- Recheck persisted eligibility immediately before issuance. UI visibility is not authorization. Only a server-validated `AUTHORIZED` record with complete trusted CAE/type/number/POS/amount data and an exact authorized-total match is printable. `UNKNOWN` with reconciliation-required metadata is unresolved, non-printable and non-retryable until authoritative reconciliation resolves it.
- Return minimal serializable payment/voucher DTOs only. Never send credentials, raw AFIP payloads/responses, error objects or unrestricted Prisma records to a client or print component.

### R5 — Ledger row and print UI

- On every individual payment row in account-ledger detail (the row currently showing payment method/amount/date in “Historial de Pagos”), show an accessible icon button with a text/tooltip label identifying its state/action. Do not put the only action on the order-level list where payments are not represented individually.

### R6 — Error handling, retries and observability

- Use finite explicit statuses and transitions; impossible transitions (e.g. `AUTHORIZED -> ISSUING`, a second concurrent `PENDING -> ISSUING`, or `NOT_REQUIRED -> ISSUING`) are rejected in the database/application boundary. `NOT_REQUIRED` is terminal for invoice actions.
- Local duplicate requests for the same A/B/C payment/type while `PREPARING`/`ISSUING` return the current attempt state without another POST. An already `AUTHORIZED` payment returns the existing voucher and never emits again, even if the client requests a different type. A `NOT_REQUIRED` payment returns/preserves its intentional no-AFIP state and never starts an attempt, regardless of repeated calls.
- Allow a manual A/B/C retry only from missing or definite `FAILED` and only after resource, payment amount, authorization, feature entitlement, configured POS and A/B/C type are revalidated. Every retry has a durable attempt number. Never allow retry/create/reconciliation from `NOT_REQUIRED`. Do not retry automatically on browser/network/action errors.
- Separate payment-write status from voucher-issuance status. If payment persistence succeeded and voucher creation failed, keep the payment, return/report “payment recorded; invoice not issued” (or “verify issuance” for unknown), and allow the ledger row control to recover later. Never roll back/delete a recorded payment to hide an AFIP failure.
- Log allowlisted event/failure codes, payment-voucher/attempt IDs, business/order/movement IDs, phase, type, whole-peso amount, and whether external issuance started. Exclude full CUIT, client document data, CAE, tokens, certificates, keys, internal key, raw payload, raw provider diagnostics and stack/error data. Use a safe user-facing message plus a server diagnostic code.

## Explicit assumptions and unresolved fiscal blocker

### Assumptions for implementation

1. “All supported AFIP invoice types” means the current electronic invoice types accepted by this codebase: Factura A/B/C (WSFE 1/6/11), not Remito, Presupuesto or Nota de Crédito. The payment form separately offers Remito as the explicit no-AFIP option specified here; it is not an AFIP invoice type. If supported invoice types change independently, the invoice selector must use the server's validated set rather than a client-only list.
2. “Each individual payment” means one independently issued invoice per persisted `CashMovement` record, not one invoice for each order and not one invoice per cash-method split within a single movement.
3. A newly recorded A/B/C payment should automatically start voucher creation after commit, while the per-row create/retry control is the recovery path for missing/definite failures. An issuance failure never makes the payment transaction fail.
4. Remito is an explicit payment-level no-AFIP choice persisted as `NOT_REQUIRED` atomically with its `CashMovement`. It records the same normalized payment exactly once, preserves existing order/client accounting, and creates no AFIP invoice/attempt, payment-specific paper Remito or separate cash movement. The ordinary full-sale Remito checkout/printing path is unrelated and unchanged. No legal conclusion is made by using the Remito label.
5. For A/B/C, the payment amount is the authoritative gross invoice total; the requested payment is normalized to a positive integer whole-peso amount before persistence and that saved amount is immutable for the voucher attempt. Remito records that same normalized payment amount but has no invoice total or AFIP authorization.
6. Recipient data is read from the persisted linked Client on the server at each A/B/C attempt reservation time; client-supplied identity/IVA fields are never accepted by the voucher action. The linked Client is edited once through the account-level editor, and its saved fiscal condition/identity is the shared source for subsequent attempts on all payment rows for that account. A Factura B request/snapshot always uses `Consumidor Final` for recipient IVA, without changing saved Client data. The user's Factura A selection supports exactly one CUIT or DNI input at the application boundary, but this does not establish AFIP acceptance. Remito uses no recipient snapshot.
7. The order's `clientId` must resolve to a Client for the persistent edit and A/B/C server-derived recipient snapshot. For an order with no linked Client, A/B/C must fail before external issuance with a safe “customer data required” result; do not create a Client, attach one to the Order, or substitute mutable/order-invoice fields silently. Remito does not need recipient data to record the no-AFIP payment. Whether account-ledger should offer a separate create-and-link customer workflow for invoice issuance is outside this feature and requires product approval if clientless payments must be supported.
8. The remote `createVoucher` endpoint has no demonstrated idempotency key or specific voucher-reconciliation endpoint in this repository. The safe fallback is fail-closed `UNKNOWN` plus manual/authoritative reconciliation, never blind retry. This applies only to A/B/C attempts; `NOT_REQUIRED` is a deliberate no-call state, not an unresolved outcome.

### Blocking ambiguity — IVA/tax classification of “Pago parcial”

The application contract observed in `src/utils/billing.ts` and `src/lib/server/afip-voucher.ts` sends generic product fields, `billType`, customer IVA/document fields and totals to an external `createVoucher` function; it does not expose a per-line IVA rate/category in this repository. The external function source/contract was not available to inspect here. A generic description by itself does not determine a fiscal IVA treatment, and this architecture must not invent a rate or assume an “advance” has a tax treatment that the current function does not actually implement.

**Before implementation can be considered fiscally complete, confirm from the remote function's current documented behavior (or its owner) that a one-line `Pago parcial` at quantity 1 uses the existing invoice-path tax treatment for the selected A/B/C and persisted customer IVA condition, and that its authorized invoice total equals the submitted normalized whole-peso payment amount.** If it cannot, the remaining business/fiscal decision is which legally approved IVA treatment the line uses for each supported invoice type/customer condition. Do not solve that by hard-coding a rate, altering the saved payment total, or changing the user's chosen generic line/type. The application must compare the request and trusted authorized response amount exactly in whole pesos and must not present a mismatch as a successful payment voucher.

This uncertainty does not reopen the user's decisions about a generic line or per-payment Factura, but it **does block fiscal sign-off/implementation release** if the endpoint cannot satisfy the exact-total and tax-treatment requirements. The safe failure/reconciliation behavior above remains required regardless.

### Narrow remaining fiscal validation — Factura A recipient document

The application already represents recipient identity as a document type (`CUIT` or `DNI`) and a text document number in `BillParametersForm`/`BillState`, and the confirmed feature contract lets the operator save/select exactly one such pair for the requested Factura A recipient. The checked-in code does not establish that the external gateway accepts both options, or which validation conditions apply to each Factura A case. The gateway/API owner or fiscal owner must confirm the permitted type/number combinations and validation before making a fiscal-acceptance claim. Until then the app can implement the explicit UI/data contract and surface a safe pre-issue/definite upstream rejection, but must not present local validation as legal authorization or auto-substitute the other document type. This is separate from (and does not remove) the generic-line IVA/exact-total blocker above.

## Acceptance criteria

- **AC-01 — Per-payment uniqueness:** for any two distinct `CashMovement` rows on one order, each may receive its own voucher record even when the amount is equal; for one movement, concurrent/replayed requests create no more than one associated voucher and no more than one active remote issuance attempt.
- **AC-02 — Existing order invoice preserved:** for payments on an order with an existing invoice, A/B/C voucher create, all failure/retry/reconciliation paths, authorized print, and Remito/no-AFIP selection leave every `Order` invoice field unchanged; payment-voucher fiscal fields/decision are associated only with `CashMovement`, never stored on or substituted for the order invoice.
- **AC-03 — Generic single line:** every valid create request sent to AFIP contains exactly one product line with description exactly `Pago parcial`, amount/quantity `1`, no discount, and request total/total-with-discount numerically equal to the payment snapshot; it contains no order items and never uses order total/balance as invoice total.
- **AC-04 — Whole-peso input normalization:** positive ARS user inputs and stored order/payment source amounts use standard `Math.round` nearest-whole-peso semantics (halves up) at their defined boundaries. `10.5` input is persisted as 11; an input equal to `0.1 + 0.2` normalizes to 0 and is rejected because the post-round value is below 1 peso. Both A/B/C and Remito persist one movement with the saved integer 11. For A/B/C, the AFIP request/voucher/print use 11 and trusted authorized response evidence is checked against 11 exactly, never rounded. Remito has no invoice or print total. No fractional amount is preserved as the payment amount.
- **AC-05 — Selection, mapping and AFIP rejection:** at payment registration the operator can select Factura A/B/C or Remito. A/B/C server validation maps only those invoice types to 1/6/11 and keeps the existing invoice flow. Remito is accepted only as the explicit payment-registration no-AFIP choice; it is not mapped to an AFIP type and is rejected by all AFIP create/retry boundaries, as are Presupuesto, credit notes, unknown values and forged AFIP type codes.
- **AC-06 — Session/tenant/resource authorization:** unauthenticated, missing-business, cross-business, forged business/order relation, missing payment or unauthorized attempts return safe failures. For A/B/C, unentitled businesses and invalid credentials/POS also cause a safe failure and zero `createVoucher` calls. Remito requires normal payment/tenant authorization but is not blocked by AFIP entitlement, credentials or missing POS, and makes zero AFIP calls. Authorization is enforced in every Server Action regardless of rendered UI.
- **AC-07 — Transaction/remote boundary:** for A/B/C, payment/voucher reservation and status transition commit before any network call; no Prisma transaction remains open during sequence lookup or `createVoucher`; the response is finalized in a separate short transaction. For Remito, payment and `NOT_REQUIRED` association commit atomically, and no network or AFIP transaction phase is entered.
- **AC-08 — Payment survives fiscal failure:** once a payment row is committed, any subsequent AFIP failure leaves that `CashMovement` and order balances intact, reports payment success separately from voucher outcome, and makes the failed/missing voucher recoverable from that individual ledger payment row.
- **AC-09 — Durable duplicate prevention:** duplicate same-payment requests while processing return current state and produce one remote create call; `AUTHORIZED` requests return the same stored CAE/voucher and create zero further remote calls. A retry from definite `FAILED` increments a durable attempt and produces at most one call for that attempt.
- **AC-10 — Ambiguous outcome safety:** a timeout, process-crash/stale `ISSUING`, malformed/indeterminate response, or persistence failure after possible remote dispatch results in `UNKNOWN`; no automatic or operator “retry” path can dispatch another call until authoritative reconciliation establishes the prior attempt was not authorized. A confirmed existing voucher is attached without creating a replacement; confirmed absence/rejection can be retried.
- **AC-11 — Phase-classified issuance failure:** every issuance failure is classified by whether the actual HTTP transport could have been invoked, not by a flag set before entering the AFIP adapter. The durable dispatch-marker callback is executed by the adapter only after all deterministic validation, mapping, reservation and request preparation, and immediately before `axios.post`; no transport call may occur if the marker cannot be durably recorded. Any failure before that marker (including validation, reservation, configuration/credentials, sequence lookup, mapping, DTO construction, serialization, and request preparation) is a visible, safe, definite `FAILED` outcome with no printable CAE data and is manually retryable only after revalidation. After the marker, an exception may be `UNKNOWN` unless an unambiguous upstream rejection confirms no voucher was authorized; ambiguous post-dispatch outcomes block retry pending reconciliation.
- **AC-12 — Exact authorized total:** compare the trusted AFIP-returned total and any later authoritative reconciliation total as an exact numeric decimal value against the immutable whole-peso amount saved on the movement, using decimal-safe parsing/comparison rather than binary-float rounding. Do not round, truncate, apply epsilon/tolerance, or otherwise normalize provider/reconciliation evidence. Numeric or textual forms `123`, `123.0`, and `123.00` are exact matches for expected 123; `123.4` is non-whole and a mismatch even though rounding it would produce 123. Only an exact match can reach normal `AUTHORIZED`/printable status; the voucher amount remains exactly the saved movement amount. For a successful response with a non-whole or mismatched total, preserve bounded exact observed-total evidence and safe allowlisted reconciliation-required metadata while persisting the existing status `UNKNOWN`; block printing and replacement issuance, and do not alter payment/order amounts or retain raw provider payloads. A later reconciliation may attach/authorize a voucher only after the same exact comparison passes; non-whole or mismatched reconciliation evidence leaves it unresolved and non-printable. Fiscal sign-off also verifies that the generic line's tax classification matches the approved existing gateway behavior.
- **AC-13 — Ledger row UI:** each payment row in account-ledger detail has only its own accessible voucher-lifecycle controls. Missing/definite A/B/C failure offers create/retry and requires an explicit A/B/C invoice-type selection; `ISSUING` disables duplicate submit; `UNKNOWN` offers reconciliation guidance but no retry; `AUTHORIZED` offers print. `NOT_REQUIRED` shows a passive “Sin emisión AFIP (Remito)” state and no create, print, retry, or reconciliation action. No payment row has a customer fiscal edit button/dialog.
- **AC-14 — Independent print:** an authorized payment voucher print uses only its own CAE/type/number/POS/date/trusted fiscal snapshot and one `Pago parcial` line with the exact paid amount. It is printable repeatedly without DB mutation or network issuance; neither order CAE appears on it nor payment CAE on the original order invoice.
- **AC-15 — Error privacy and minimal data:** action results, UI errors and logs contain only safe user-facing text and allowlisted diagnostic fields; no credentials, keys, tokens, raw AFIP payload/response, raw Error objects or unrestricted Prisma records cross the client boundary. Full client fiscal identifiers (document type/number) must not appear in general payment, status, client-list, or other action DTOs, UI errors, logs, or arbitrary Prisma serialization. The sole client-boundary exception is the purpose-specific `AuthorizedPaymentVoucherPrintDTO`, returned only by its independently authorized print action for a verified `AUTHORIZED` voucher; it may include the recipient document type/number needed to display and print invoice recipient identity, and those values must come only from that voucher's immutable authorized-attempt snapshot. This exception does not permit returning raw AFIP payloads/responses or secrets and does not relax tenant/resource authorization.
- **AC-16 — Legacy compatibility:** pre-existing `CashMovement` rows with no payment-voucher decision remain readable and show the existing create action; no migration/backfill fabricates a voucher or Remito decision, no existing order-invoice/Remito printing behavior changes, and no new voucher is attached to an order without a payment movement.
- **AC-17 — Fiscal contract blocker resolved:** before release, documentation or an isolated integration contract check proves the existing remote invoice gateway accepts the generic one-line payload, applies the approved existing IVA treatment, and returns an authorized gross total equal to the submitted normalized whole-peso payment amount for each supported A/B/C case. If not proven, do not claim this criterion passes or invent a tax rate; obtain the narrow tax-treatment decision from the fiscal/API owner.
- **AC-18 — Account-level persistent Client edit:** the linked Client field/fiscal identity in account-ledger detail is clickable/editable and opens one populated, accessible account-level modal. If the typed pair is absent and legacy `Client.cuit` is populated, the editor presents that value as CUIT. There are no customer fiscal edit buttons/dialogs on individual payment rows. Saving uses the independently authenticated, business-scoped `updateClient` action and atomically persists IVA condition and the optional CUIT-or-DNI pair with the legacy field synchronized: CUIT writes the same number to typed identity and `cuit`; DNI writes the typed DNI pair and clears `cuit`; explicit clearing nulls both typed fields and `cuit`. It validates both-or-neither, preserves leading zeroes, refreshes Client data, and changes neither the Order relation nor any Order billing/fiscal field. Future create/retry attempts for every payment on the account resolve the same linked Client's current effective identity server-side (typed pair first, otherwise legacy CUIT fallback); no caller-provided customer/IVA/document values are trusted. Each attempt snapshot is immutable, as are authorized print snapshots after later Client edits. Changing document type immediately clears the old number in the modal; saving the new type requires entering its number, or clearing identity atomically persists all three fields as absent. The server rejects type-only/half updates that retain the prior type's number.
- **AC-19 — Factura A identity selection:** the Factura A attempt can carry either one CUIT/document number pair or one DNI/document number pair, never both and never a type without its number. The app UI/DTO mirrors `newBill`'s available identity names/types and number-as-text behavior but does not hide the Factura A identity controls solely because saved IVA is Consumidor Final. The attempt and print snapshot preserve exactly the selected type and string number. Application acceptance of these inputs is not treated as proof of AFIP legality; release retains the gateway/owner validation blocker and never silently swaps identifier types.
- **AC-20 — Factura B forced recipient IVA:** when `billType` is Factura B, the exact `Consumidor Final` string is used in the AFIP recipient DTO, immutable attempt recipient snapshot, authorized payment-voucher fiscal snapshot, status/print DTO and printed recipient condition, irrespective of the saved Client IVA condition. No write changes `Client.ivaCondition`; after issuance it remains exactly the saved value. A/B/C otherwise retain selected operator type and existing safety/mapping rules.
- **AC-21 — Configured POS selection on initial A/B/C payment:** before Factura A/B/C payment registration and automatic voucher attempt, the operator can view/select a POS from the authenticated business's configured `Business.ptoVenta`; default is the first configured POS when available.
